Why this matters now

You probably spend hours a day on the web without seeing any of it: every TikTok scroll, online order or school portal login triggers requests across DNS servers, CDNs, APIs and databases in milliseconds. Modern web apps now run offline as progressive web apps, stream AI-generated responses in real time and must stay fast and accessible for billions of users on every kind of device.

In this topic you will explore the syllabus content on how data moves across the internet, web protocols and ports, securing the web, front-end and back-end development, databases, big data and the role of the W3C.

Applications of Web Programming

🎯 (SE-12-03)

📌 Explore the applications of web programming

  • interactive website/webpages

Interactive Websites and Webpages

Interactive websites use client-side JavaScript to respond to user actions in real time — without requiring a full page reload. The Document Object Model (DOM) is the programming interface that allows JavaScript to read and manipulate the structure, style, and content of a live HTML page. Examples include form validation, dropdown navigation, image carousels, and live search filtering. Modern Single Page Applications (SPAs) such as those built with React or Vue extend this further, dynamically rendering entire pages client-side.

A worked example shows what "without a full page reload" means. This JavaScript listens for typing in a search box and hides the list items that do not match, so the page filters instantly and nothing is sent to the server.

JavaScript: live search filter (runs in the browser)
const box = document.querySelector('#search');
const items = document.querySelectorAll('#game-list li');

box.addEventListener('input', () => {              // fires on every keystroke
  const term = box.value.toLowerCase();
  items.forEach(li => {
    li.hidden = !li.textContent.toLowerCase().includes(term);
  });
});

If the list holds Reef Runner, Kelp Quest and Star Sailor, typing qu leaves only Kelp Quest visible, and clearing the box brings all three back. The input event is the trigger, the DOM is the thing changed, and the rest of the page is untouched.

E-Commerce

E-commerce platforms use web programming to support the entire buying lifecycle: product browsing, shopping cart management, payment processing, and order tracking. Key technical requirements include secure HTTPS connections (to protect payment data), session management (to maintain cart state across pages), database integration (to query product catalogues and stock levels), and integration with payment gateway APIs (such as Stripe or PayPal). Examples include Amazon, eBay, and Shopify-powered stores.

A checkout is a good example of front-end and back-end work being shared. The browser makes the page easy to use, but every step that involves money or stock is finished on the server.

Progressive Web Apps (PWAs)

PWAs are web applications built with standard web technologies (HTML, CSS, JavaScript) that offer a native-app-like experience. They are installable on the user's home screen, can work offline via service workers, and receive push notifications. Starbucks and Pinterest are companies that have released PWAs. PWAs are significant because they eliminate the need for a separate iOS/Android codebase while still appearing as a native application to the end-user.

Scenario A local bakery wants to take pre-orders. An interactive page shows today's stock and updates the total as customers choose items; e-commerce features take a secure card payment; and making it a PWA lets regulars add it to their home screen and reorder with one tap, without the cost of building separate iOS and Android apps.

How Data Is Transferred on the Internet

🎯 (SE-12-03)

📌 Investigate and practise how data is transferred on the internet

  • data packets
  • internet protocol (IP) addresses, including IPv4
  • domain name systems (DNS)

Data Packets

When data is sent over the internet, it is broken into small, manageable units called data packets. Each packet contains a header (addressing and control information) and a payload (the actual data fragment). Packets from the same transmission may take different routes through the network and are reassembled in the correct order at the destination. This packet-switching model means the failure of one route does not disrupt the overall transmission — other paths are used instead.

Two layers of headers travel with each packet. The IP header carries the source and destination IP addresses, a hop limit (so a packet lost in a loop is eventually discarded) and the protocol that comes next. The TCP header carries the source and destination port numbers, the sequence number and a checksum for error detection. The payload is one slice of the message.

Worked example: one reply, three packets

GameShelf's server sends a 2,400-byte page to a browser. Suppose the network allows 1,000 bytes of payload per packet (real limits are about 1,500 bytes for the whole packet, but round numbers keep the arithmetic clear). The page needs 2,400 ÷ 1,000 = 2.4, rounded up to 3 packets.

PacketSequence (byte offset)PayloadWhat happens
10bytes 0 to 999Arrives first via router A
21000bytes 1000 to 1999Lost on the way (a router is overloaded)
32000bytes 2000 to 2399Arrives second via router B, so it is out of order
  1. The browser acknowledges packet 1 ("I have everything up to byte 999").
  2. Packet 3 arrives but the next expected sequence number is 1000. The gap tells TCP that packet 2 is missing, so it keeps packet 3 and does not acknowledge past byte 999.
  3. The server gets no acknowledgement for packet 2 in time and retransmits it.
  4. Packet 2 arrives. TCP now has bytes 0 to 2399 in order and hands the complete page to the browser.

This is why the web feels reliable even though the network underneath does not promise delivery. Before any of this, TCP opens the connection with a three-way handshake: the client sends SYN, the server replies SYN-ACK, and the client answers ACK.

IP Addresses and IPv4

Every device on a network is assigned an Internet Protocol (IP) address — a unique numerical label used to identify it for communication purposes. IPv4 (Internet Protocol version 4) addresses are 32-bit numbers expressed in dotted-decimal notation, divided into four octets (e.g., 192.168.1.1). IPv4 supports approximately 4.3 billion unique addresses. Due to address exhaustion, Network Address Translation (NAT) is used so that multiple devices on a private network can share a single public IP address. IPv6 was introduced to address this limitation using 128-bit addresses.

Worked example: reading an IPv4 address

An IPv4 address is 32 bits, written as four octets of 8 bits, each shown as a decimal number from 0 to 255. Converting 192.168.1.1 one octet at a time:

Domain Name System (DNS)

The Domain Name System (DNS) translates human-readable domain names (e.g., www.google.com) into machine-readable IP addresses (e.g., 142.250.70.142). When a user types a URL, the browser queries a DNS resolver (usually provided by their ISP), which traverses a hierarchy of DNS servers (Root → TLD → Authoritative) to resolve the domain. The resolved IP address is then cached locally (for a duration defined by TTL — Time To Live) to speed up future requests.

DNS Resolution Order Browser cache → OS cache → Router cache → ISP Resolver → Root Name Server → TLD Server (e.g., .com) → Authoritative Name Server → IP address returned.

Worked example: resolving a name

A student opens www.gameshelf.example (a made-up name, so it will not resolve on the real internet) for the first time. The steps are the same for any real site:

  1. The browser checks its own DNS cache, then the operating system's cache. Both miss.
  2. The OS asks the configured resolver (usually run by the ISP or the school network). It has no cached answer either.
  3. The resolver asks a root server, which does not know the address but says which servers look after the .example top-level domain.
  4. The TLD server does not know the address either but names the authoritative name server for gameshelf.example.
  5. The authoritative server answers with the record, for instance an A record giving an IPv4 address, and a TTL (time to live) such as 3600 seconds.
  6. Every cache on the way back keeps the answer for the TTL, so the next lookup within the hour is answered instantly and no root, TLD or authoritative server is asked.
RecordHoldsUsed for
AAn IPv4 addressFinding the web server for a name
AAAAAn IPv6 addressThe same, for IPv6
CNAMEAnother name (an alias)Pointing www at the main name, or at a CDN
MXThe mail server for the domainTelling SMTP where to deliver email

The TTL explains the "Try this" above: a changed address keeps being served from caches until each TTL runs out, so the change spreads over minutes to hours.

Hands-on: watch it happen

  1. Open a terminal and run nslookup www.education.nsw.gov.au (on macOS or Linux, dig www.education.nsw.gov.au is an alternative). You should see the resolver that answered and one or more addresses. The exact numbers can change between runs and between networks; that is normal.
  2. Run tracert www.education.nsw.gov.au on Windows, or traceroute www.education.nsw.gov.au on macOS and Linux. Each numbered line is one router (a hop) that the packets crossed, with its response time. Some lines may show * because a router does not answer.
  3. Run ping 127.0.0.1. Every reply comes from your own computer, which is the loopback address described above.

Ports: which program should receive the data?

An IP address finds the computer; a port is a 16-bit number (0 to 65,535) that finds the program on that computer. A web server, a mail server and an SSH server can all run on one machine because each listens on its own port. Ports 0 to 1023 are the "well-known" ports reserved for standard services such as those in the table, 1024 to 49151 are registered for particular applications, and the rest are used for short-lived connections that a client opens. When you visit https://www.gameshelf.example/games?max_cost=30 the browser fills in port 443 itself, because it is the default for https. Writing http://localhost:8000 names a different port, which is how a program under development is usually reached.

Where each protocol sits

Protocols work in layers, each relying on the one below. This is why a question can ask "which protocol finds the address, which delivers it reliably and which carries the page?" and expect three different answers.

LayerJobProtocols in this dot point
ApplicationDefines the conversation for one kind of serviceHTTP, HTTPS, FTP, SFTP, SMTP, POP3, IMAP, DNS
SecurityEncrypts and authenticates the connectionTLS (and its predecessor SSL); SFTP uses SSH for the same purpose
TransportDelivers data to the right program, in order and complete (or not)TCP (reliable, ordered); UDP (fast, no guarantees) is used by most DNS queries
InternetAddresses and routes packets between networksIP (IPv4 and IPv6)

TCP suits web pages, files and email, where a missing byte would corrupt the result. UDP suits things such as a DNS lookup or a live video call, where a fast answer matters more than resending every lost packet. HTTP/3, the newest version of HTTP, runs over a UDP-based transport called QUIC, but the syllabus expects the classic picture of HTTP over TCP.

HTTP in detail: one request, one response

HTTP is a text-based request and response protocol. The browser sends a request line, headers and, for some methods, a body; the server answers with a status line, headers and a body. Email: sending and collecting are different jobs

SMTP only sends and relays mail: your phone hands the message to your provider's server over SMTP, and that server hands it on to the recipient's server over SMTP. To collect the mail, the recipient's device uses IMAP, which keeps the mail on the server and synchronises every device, or POP3, which downloads it (usually removing it from the server). A person who reads email on a phone and a laptop needs IMAP, because with POP3 each message would end up on only one of them.

Insecure and secure versions

Several of the protocols above have a version that adds encryption. The insecure ones send passwords and content as readable text, so anyone on the path (a shared Wi-Fi network, for example) can read them.

SSL/TLS Certificates

An SSL/TLS certificate is a digital document issued by a trusted Certificate Authority (CA) (e.g., Let's Encrypt, DigiCert) that verifies a website's identity and enables encrypted HTTPS connections. When a browser connects to a site, it checks that the certificate is: (1) issued by a trusted CA, (2) not expired, and (3) issued for the correct domain. Without a valid certificate, browsers display a "Not Secure" warning, deterring users and search engines alike.

A certificate is a small signed file with a fixed set of fields. Browsers trust it because of a chain of trust: the server's certificate is signed by an intermediate authority, whose certificate is signed by a root authority, and the root certificates are already stored in the browser or operating system. The browser never has to know the website in advance; it only has to trust the root.

Certificate fieldExampleWhat the browser does with it
Subject (the domain)www.gameshelf.exampleCompares it with the address in the URL bar; a mismatch means a warning

A certificate proves that whoever controls the domain asked a CA for it. It does not prove that the site is honest: a scam site can have a valid certificate for its own domain. The padlock means "your connection to this domain is encrypted", not "this site is safe".

Encryption Algorithms

Encryption algorithms transform readable plaintext into unreadable ciphertext, protecting data from interception. Symmetric encryption (e.g., AES-256) uses a single shared key for both encryption and decryption — fast and efficient, but the key must be securely exchanged beforehand. Asymmetric encryption (e.g., RSA-2048) uses a mathematically linked key pair: a public key to encrypt and a private key to decrypt. TLS uses asymmetric encryption to securely exchange a session key, then switches to faster symmetric encryption for the remainder of the connection.

Encryption Keys

An encryption key is a string of bits used by an algorithm to encrypt or decrypt data. Public keys are freely shared and used to encrypt data sent to the key's owner. Private keys are kept secret by the owner and used to decrypt data or create digital signatures. Key length determines security strength: a 256-bit AES key has 2256 possible combinations, making brute-force attacks computationally infeasible.

Worked example: plain text to cipher text

Real algorithms such as AES are far stronger, but a Caesar cipher shows the vocabulary. The algorithm is "shift each letter along the alphabet"; the key is how far (here 3). Anyone who knows the algorithm still cannot decrypt without the key, and that is the point of having a key.

Python: a Caesar cipher (a teaching example, not real security)
def caesar(text, key):
    result = ""
    for ch in text:
        if ch.isalpha():
            base = ord("A") if ch.isupper() else ord("a")
            result += chr((ord(ch) - base + key) % 26 + base)
        else:
            result += ch                     # leave digits and symbols alone
    return result

plain_text = "Pay $25 to Ava"
cipher_text = caesar(plain_text, 3)          # encrypt with key 3
print(cipher_text)
print(caesar(cipher_text, -3))               # decrypt: shift back by the same key
Output
Sdb $25 wr Dyd
Pay $25 to Ava

A Caesar cipher has only 25 useful keys, so a computer tries them all in an instant. AES-256 has 2256 keys, which is why key length matters, and why a good algorithm is one that stays secure even when everyone knows how it works.

Authentication and Authorisation

Authentication is the process of verifying who a user is (e.g., verifying a username and password match a database record). Authorisation is the process of verifying what an authenticated user is permitted to do (e.g., checking if a logged-in user has the "admin" role before allowing access to the dashboard). Modern web applications use JSON Web Tokens (JWT) or OAuth 2.0 to manage these processes securely across multiple services.

A school portal asks two separate questions on every protected request, and the HTTP status code tells you which one failed.

ROLES = {"ava": "admin", "ben": "student"}          # in real life: a database table

    return ROLES.get(username) == "admin"           # only admins may delete

False

Multi-factor authentication (MFA) strengthens the first question by asking for two different kinds of proof: something you know (a password), something you have (a phone or security key) or something you are (a fingerprint). Two passwords are not two factors, because both are things you know.

Cookies and sessions

HTTP is stateless, so after you log in the server needs a way to recognise your next request. It does this with a session: the server creates a record (who you are, what is in your cart) and gives the browser a long random session ID in a cookie. The browser sends the cookie automatically with every later request to that site, and the server looks the session up.

Hash Values

A hash function is a one-way mathematical function that converts any input into a fixed-length output called a hash value (or digest). For example, the SHA-256 algorithm produces a 64-character hexadecimal hash. Hash functions are deterministic (same input always produces the same hash) but irreversible — it is computationally infeasible to reconstruct the original input from the hash. Web applications use hashing to store passwords securely: the hash of the password is stored, never the password itself. Algorithms like bcrypt add a random salt before hashing to prevent rainbow table attacks.

Digital Signatures

A digital signature is a cryptographic mechanism that proves the authenticity and integrity of a message or document. The sender hashes the content, then encrypts the hash with their private key to produce the signature. The recipient decrypts the signature using the sender's public key and compares it to their own hash of the received content. If they match, the message has not been tampered with and genuinely originated from the claimed sender. Digital signatures provide non-repudiation — the sender cannot later deny having sent the message.

Worked example: hashing a password

A hash has three properties you can see for yourself: the same input always gives the same output, the output has a fixed length, and a tiny change to the input gives a completely different output.

Python: SHA-256 and a salted, slow hash
import hashlib

for password in ["password1", "Password1"]:
    print(password, hashlib.sha256(password.encode()).hexdigest())

print(hashlib.pbkdf2_hmac("sha256", b"password1", b"Q7pd", 100_000).hex()[:32])

The TLS handshake step by step

The animation above shows the idea. The handshake that makes it happen has these steps, at the depth the syllabus needs:

  1. The browser opens a TCP connection to port 443, then sends a ClientHello listing the TLS versions and cipher suites (algorithm combinations) it supports.
  2. The server replies with the choice it made, and sends its certificate, together with proof that it holds the matching private key.
  3. The browser checks the certificate: signed by a trusted CA, still in date, and issued for exactly this domain. If any check fails, the user sees a warning.
  4. Both sides use a key exchange to work out the same session key. The key itself never crosses the network in a form an eavesdropper can use.
  5. Each side sends a Finished message, protected by the new key, to prove nothing was altered during the handshake.
  6. From here, the HTTP request and response are encrypted with fast symmetric encryption using the session key.

Cross-site scripting (XSS)

Encryption protects data on its way to the site; it does nothing if the site itself sends the attacker's code to other users. The Course Specifications describe cross-site scripting as injecting malicious code into an otherwise safe website, usually through user input that is not sufficiently sanitised before it is processed and stored on the server. Students are expected to interpret JavaScript fragments about it.

JavaScript: a vulnerable comment box
const comment = document.querySelector('#comment').value;      // whatever the user typed
document.querySelector('#comments').innerHTML += '<p>' + comment + '</p>';

The fault is innerHTML combined with unchecked input: the browser treats the text as HTML, so any tags in it become real elements. If an attacker submits <img src="x" onerror="alert('XSS')"> the image fails to load, the onerror code runs, and the same thing happens for every visitor who is shown the comment. This is a stored attack when the server saves the comment and serves it to everyone. It is a reflected attack when the input comes from the URL and is echoed straight back on the page. In place of an alert, real attacks try to read the page, submit forms as the user or steal cookies.

JavaScript: the fix, treat input as text
const comment = document.querySelector('#comment').value;
const p = document.createElement('p');
p.textContent = comment;                       // shown as text, never run as HTML
document.querySelector('#comments').appendChild(p);

On the server, the same defence is output encoding: turning characters such as < into &lt; before they go into a page. Template engines such as Jinja2 do it automatically for template variables, and Python's html.escape does it by hand:

Python: escaping user input
import html
print(html.escape("<script>alert(1)</script>"))
Output
&lt;script&gt;alert(1)&lt;/script&gt;

The browser now displays the characters instead of running them. Defence in depth adds validation on input (reject or limit what is not expected), a Content Security Policy header that stops inline scripts running, and HttpOnly cookies so a script cannot read the session ID even if one gets through. Compare this with SQL injection, which attacks the database using unchecked input; the parameterised queries in the SQL section are its defence.

Big data is usually described by three properties, the "three Vs": volume (too much to store on one server), velocity (arriving continuously, such as clicks and video views) and variety (text, images, video and logs together). A web application that must store and process data like this cannot rely on a single server and one database, so its architecture changes.

Data Mining

Data mining is the process of discovering patterns, correlations, and insights within large datasets using statistical and machine learning techniques. Web platforms mine user interaction data (clicks, search queries, time on page) to personalise recommendations, optimise advertising, and predict future behaviour. For example, Netflix mines viewing history to recommend shows; Google mines search patterns to rank results. Ethical concerns include user consent, data sovereignty, and the potential for discriminatory algorithmic outcomes.

Worked example: mining a pattern

GameShelf stores five customers' baskets. Data mining looks for items that appear together. Two measures are widely used: support (how many of all baskets contain both items) and confidence (of the baskets with the first item, how many also have the second).

Python: does buying Reef Runner predict buying Kelp Quest?
baskets = [
    {"Reef Runner", "Kelp Quest"},

with_both = sum(a in basket and b in basket for basket in baskets)

print("baskets with", a + ":", with_a)
print("baskets with both:", with_both)
print("support:", with_both / len(baskets))

It also shows the ethical limit: the recommendation is useful, but the same method applied to health or location data could reveal things people never chose to share.

Metadata

Metadata is "data about data" — descriptive information that provides context about other data without being the primary content itself. On the web, metadata includes HTTP headers (content type, cache directives), HTML <meta> tags (page description, author, viewport settings), and file metadata (creation date, author, geolocation embedded in photos). Metadata is critical for search engine indexing (SEO), content management, and security analysis. Importantly, metadata can reveal sensitive information even when primary content is private — for example, a photo's EXIF data can expose a user's exact GPS location.

Worked example: metadata you can inspect

Metadata is often invisible but easy to find. Every HTTP response carries some, every page can carry more in its <head>, and every photo carries its own.

Streaming Service Management

Streaming services (e.g., YouTube, Netflix, Spotify) manage enormous volumes of concurrent data delivery. Key architectural solutions include: Content Delivery Networks (CDNs) — geographically distributed server networks that cache and serve content from the nearest node to reduce latency; Adaptive Bitrate Streaming (ABR) — which dynamically adjusts video quality based on the user's current bandwidth; and load balancers that distribute incoming requests across multiple server instances to prevent any single server from being overwhelmed.

How a streaming service copes with millions of viewers

  1. Each video is encoded several times, at different quality levels, and cut into short segments of a few seconds. A small text file (a manifest) lists the segments for each quality.
  2. The segments are copied to CDN servers in many cities. When you press play, DNS or the CDN's routing sends you to a nearby one, which cuts latency and keeps traffic off the origin server.
  3. The player fetches segments one at a time and measures how quickly they arrive. This is adaptive bitrate streaming: if the connection slows it asks for the lower-quality version of the next segment, so the picture gets softer instead of freezing.
  4. A load balancer spreads requests for the site itself (search, login, recommendations) across many identical servers, and stops sending traffic to any that fail. When a popular show is released, more servers are started to cope.
  5. Viewing events (play, pause, stop) stream into storage where they are mined to make recommendations.

The Role of the W3C

🎯 (SE-12-05)

📌 Investigate and explain the role of the World Wide Web Consortium (W3C) in the development of applications for the web

  • Web Accessibility Initiative (WAI)
  • internationalisation
  • web security
  • privacy
  • machine-readable data

The World Wide Web Consortium (W3C) is an international community, led by its member organisations and founded by Tim Berners-Lee, that develops open standards for the web. A standard starts as a draft, is reviewed and tested by implementers, and only becomes a W3C Recommendation once it has been shown to work in more than one browser. The value to developers is that code written to a standard behaves the same way in every compliant browser, and that no single company controls how the web works. HTML and the DOM are now maintained as a "living standard" by the WHATWG community, which works with the W3C; CSS, WCAG, WebAuthn and many other web standards are W3C's own.

Web Accessibility Initiative (WAI)

Develops the Web Content Accessibility Guidelines (WCAG) — the international standard for making web content accessible to people with disabilities (visual, auditory, cognitive, motor). Compliance levels: A, AA (the level Australian government guidance expects), AAA. Practices include alternative text for images, keyboard-navigable interfaces, and sufficient colour contrast ratios.

Internationalisation (i18n)

Ensures web technologies support all languages, scripts, and cultures globally. This includes Unicode character encoding (UTF-8), right-to-left (RTL) text support for Arabic/Hebrew, locale-specific date/number formatting, and tools for translating and localising web content without changing the underlying code structure.

Web Security

The W3C develops security-related standards such as Content Security Policy (CSP) headers (which restrict the sources from which scripts, styles, and images can be loaded, mitigating XSS attacks), Subresource Integrity (SRI) (verifying third-party CDN resources haven't been tampered with), and the Web Authentication API (WebAuthn) for passwordless login.

Privacy

The W3C's Privacy Interest Group (PING) helps review new web specifications for privacy, and W3C specifications include privacy considerations. The aim is that new browser features cannot be used for fingerprinting or tracking users without consent. Replacing third-party cookies has been proposed by browser makers (for example Google's Privacy Sandbox) and debated in W3C groups. The Do Not Track signal was never widely honoured by websites, and its W3C working group has closed. Australian law adds its own duties under the Privacy Act 1988.

Machine-Readable Data

The W3C develops standards for structured, semantic data that machines (search engines, AI systems) can interpret. This includes Schema.org vocabulary embedded as JSON-LD or microdata in HTML (enabling rich search results), the Resource Description Framework (RDF), and Semantic HTML5 elements (<article>, <nav>, <section>) that provide meaning beyond visual presentation.

Worked example: is this text readable? (WAI and WCAG)

WCAG requires a contrast ratio of at least 4.5:1 for normal text at level AA (3:1 for large text). The ratio compares the brightness of the text and background colours, from 1:1 (identical) to 21:1 (black on white). This program follows the WCAG formula for relative luminance:

Python: checking WCAG contrast against a white background
def luminance(hex_colour):
    r, g, b = [int(hex_colour[i:i + 2], 16) / 255 for i in (1, 3, 5)]
    def channel(c):
        return c / 12.92 if c <= 0.03928 else ((c + 0.055) / 1.055) ** 2.4
    return 0.2126 * channel(r) + 0.7152 * channel(g) + 0.0722 * channel(b)

def contrast(colour_a, colour_b):
    lighter, darker = sorted([luminance(colour_a), luminance(colour_b)], reverse=True)
    return (lighter + 0.05) / (darker + 0.05)

for colour in ["#000000", "#767676", "#999999", "#6366F1", "#4F46E5"]:
    ratio = contrast(colour, "#FFFFFF")
    print(colour, round(ratio, 2), "passes AA" if ratio >= 4.5 else "fails AA")
Output

#767676 4.54 passes AA
#999999 2.85 fails AA
#6366F1 4.47 fails AA
#4F46E5 6.29 passes AA

The fourth line is a useful surprise: the popular indigo #6366F1 is 0.03 short of the AA threshold for normal text on white, so a slightly darker #4F46E5 (used in the CSS examples on this page) is the safer choice. Accessibility is decided by measurement, not by whether a colour "looks fine" to the person who chose it. WCAG is organised around four principles, often remembered as POUR: content must be perceivable, operable, understandable and robust.

Client-Side (Front-End) Web Programming

The client side refers to all code that executes within the user's web browser. Front-end code consists of three complementary technologies: HTML (structure and content), CSS (visual presentation and layout), and JavaScript (interactivity and dynamic behaviour). The browser downloads these files from the server, parses them, and renders the visual page. Client-side code is visible to the user (via browser dev tools) and should never contain sensitive data such as API keys or database credentials.

Server-Side (Back-End) Web Programming

The server side refers to code that executes on the web server — invisible to the client. The server receives HTTP requests, applies business logic (authentication, data processing, calculations), queries the database, and returns a response (HTML page or JSON data). Common back-end languages include Python (Django, Flask), JavaScript (Node.js/Express), Ruby (Rails), and PHP. The server environment is protected from end-users and may contain sensitive configuration, credentials, and proprietary algorithms.

Databases — SQL and Non-SQL

SQL (Relational) Databases

Store data in structured tables with rows and columns. Relationships between tables are defined by primary and foreign keys. Enforce data integrity via ACID transactions. Examples: PostgreSQL, MySQL, SQLite. Best for: structured, consistent data with complex relationships (e.g., e-commerce orders, user accounts).

Non-SQL (NoSQL) Databases

Store data in flexible formats — documents (JSON), key-value pairs, graphs, or column families. Schema-free, allowing rapid iteration. Examples: MongoDB (documents), Redis (key-value), Neo4j (graphs). Best for: unstructured or evolving data (e.g., social media posts, real-time analytics, content catalogues).

Web Browsers and Developer Tools

🎯 (SE-12-03, SE-12-06)

📌 Explore and explain the influence of a web browser on web development, including the use of developer (dev) tools

Your code only works if the browser runs it the way you expect. Browsers use different engines, support features at different times and handle errors differently, so developers test in more than one and use the browser's built-in developer tools to find out what is really happening.

Browser Rendering Engines

Different browsers use different rendering engines to parse HTML/CSS and render the visual page: Blink (Chrome, Edge, Opera), WebKit (Safari), and Gecko (Firefox). Differences in engine implementations can cause the same CSS to render slightly differently across browsers — a core challenge of front-end development known as cross-browser compatibility. Developers use tools like Can I Use (caniuse.com) to check which CSS/JavaScript features are supported across browser versions before using them in production.

Whatever the engine, the browser follows the same pipeline, and knowing it explains many bugs and slow pages:

  1. It parses the HTML into the DOM (a tree of elements) and the CSS into a matching set of style rules.
  2. It combines them into a render tree of the elements that will actually be shown (an element with display: none is left out).
  3. It works out the layout: the size and position of every box.
  4. It paints the pixels to the screen.

A script that changes the DOM or CSS forces some of these steps to be done again, and a script or stylesheet in the <head> can hold up the first paint. Browsers also add new features at different times, so a developer either checks support on Can I Use or tests for the feature before relying on it:

JavaScript: feature detection with a fallback
if ('serviceWorker' in navigator) {
  navigator.serviceWorker.register('/sw.js');       // browser supports service workers
} else {
  console.log('No service worker support: the site still works online.');
}

In CSS the equivalent is the @supports rule. The principle is progressive enhancement: build a working baseline for every browser, then add newer features where they are available.

Consistency of Appearance

CSS enables a single stylesheet to control the visual appearance of every page across an entire website. CSS Custom Properties (variables) allow designers to define a value once (e.g., --brand-colour: #4F46E5) and reuse it throughout, ensuring colour, typography, and spacing remain consistent. Changing a single variable instantly updates every element that references it. Design systems (such as Google's Material Design or Apple's Human Interface Guidelines) are implemented through CSS to enforce consistent visual language across large products.

CSS — Variables and Responsive Design
/* Define design tokens as CSS variables */
:root {
    --primary-colour: #4F46E5;
    --font-body: 'Inter', sans-serif;
    --spacing-md: 1rem;
}

/* Apply consistently across components */
.btn-primary {
    background: var(--primary-colour);
    font-family: var(--font-body);
    padding: var(--spacing-md) calc(var(--spacing-md) * 2);
}

/* Media query for responsive design (flexibility with devices) */
@media (max-width: 768px) {
    .grid-3col { grid-template-columns: 1fr; }
}

The cascade and specificity

Several rules can set the same property on the same element, so the browser needs a rule for choosing. That rule is the cascade. It compares, in order: (1) importance (a declaration marked !important beats one that is not), (2) whether the style is inline (in the element's own style attribute), (3) specificity, and (4) source order, where the later rule wins a tie. A selector's specificity is three counts read left to right: IDs, then classes (with attributes and pseudo-classes), then element names. Compare column by column, starting at the left; a higher number in an earlier column wins no matter what is to its right.

Worked examples: which colour wins?

ElementCompeting rulesWinner and reason

<p class="red-text big">.red-text { color: red; } then .big { color: black; }Black: both are (0, 1, 0), so the later rule wins.
<p id="welcome">#welcome { color: green; } and p { color: black !important; }Black: !important is compared first. Use it sparingly; it makes styles hard to override.

The box model

Every element is drawn as a box made of four layers: content at the centre, then padding (space inside the border), the border and the margin (space outside). Most layout bugs are box-model bugs, and the Elements panel draws the four layers in colour for the selected element.

CSS: the layers of a box
.card {
  width: 200px;             /* content width */
  padding: 10px;            /* inside the border */
  border: 2px solid #333;
  margin: 20px;             /* outside the border */
  box-sizing: content-box;  /* the default: width is the content only */
}
/* Total width taken on the page: 200 + 2*10 + 2*2 + 2*20 = 264px.
   With box-sizing: border-box, width: 200px would include padding and border. */

Flexibility with Browsers and Display Devices

Responsive web design ensures a single codebase adapts to any screen size — from a 27-inch desktop monitor to a 375px mobile screen. CSS media queries apply different styles at defined breakpoints. Flexbox and CSS Grid provide flexible layout systems that redistribute space and reflow content automatically. The viewport meta tag instructs the browser to scale the page to the device's width, preventing the "zoomed-out desktop site" appearance on mobile.

Worked example: one layout, three screen sizes

Without the viewport meta tag, phones pretend to be about 980px wide and shrink the page. With it, the layout can respond to the real width. This code puts three cards in a row on wide screens and stacks them on narrow ones. It uses flexbox, relative units and one media query, with no separate mobile site.

HTML: tell the browser to use the device width
<meta name="viewport" content="width=device-width, initial-scale=1">
CSS: a flexible row that stacks on narrow screens
.cards {
  display: flex;
  flex-wrap: wrap;           /* let items drop to the next line */
  gap: 1rem;
}
.card {
  flex: 1 1 250px;           /* grow, shrink, and start at 250px wide */
  font-size: 1rem;           /* rem scales with the user's font setting */
}
@media (max-width: 600px) {
  .card { flex-basis: 100%; }   /* one card per row on phones */
}
img { max-width: 100%; height: auto; }   /* pictures never overflow their box */
  • At about 1000px wide, three 250px cards fit on one row and share the leftover space.
  • At 390px (a common phone width), only one card fits per line, so they stack; the media query makes this explicit for widths up to 600px.
  • Percentages, rem and max-width make sizes relative, so they adapt to the browser window and to users who enlarge their text. Fixed pixel widths do not.

For flexibility across browsers, developers write standard CSS, check support (Can I Use, @supports) and test in more than one engine. For flexibility across display devices, they also design for touch (tap targets of at least about 44px), for high-resolution screens (images supplied at more than one size with srcset) and for user preferences such as prefers-color-scheme and prefers-reduced-motion.

🎯 (SE-12-09)

📌 Investigate the reasons for version control and apply it when developing web application

Web projects change constantly, often with several people editing the same files. Version control records every change so you can see what changed, undo mistakes and work on new features without breaking the live site.

Version control systems (VCS) track every change made to a codebase over time, enabling developers to: roll back to any previous working state if a new change breaks functionality; branch the codebase to develop features or fix bugs in isolation without affecting the main production code; merge contributions from multiple developers working simultaneously; and maintain a complete audit trail of who changed what and why. Code Libraries for Front-End Development

🎯 (SE-12-06)

📌 Explore the types and significance of code libraries for front-end web development

  • frameworks that control complex web applications
  • template engines
  • predesigned CSS classes

A code library is pre-written code you can reuse instead of writing everything yourself. Front-end developers rely on three main kinds, which save time and make large applications more consistent.

Frameworks for Complex Web Applications

Front-end frameworks provide a structured architecture for building large, complex web applications. They enforce separation of concerns (UI components, state management, routing) and provide build tools that optimise code for production.

ReactA component-based UI library by Meta. Uses a virtual DOM for efficient re-rendering. One of the most widely used front-end libraries.
Vue.jsA progressive framework with a gentle learning curve. Combines a template-based syntax with reactive data binding. Popular for smaller to medium-scale applications.
AngularA full-featured framework by Google. Uses TypeScript, has built-in routing, forms, and HTTP client. Common in large enterprise applications.

Why frameworks are useful

The Course Specifications say students should understand why front-end frameworks are useful; they are not expected to know or code in any particular one. The reasons apply to all of them:

  • Components: the interface is built from small reusable pieces (a card, a menu, a button), each with its own markup, style and behaviour, so a change is made once.
  • Automatic updates: the developer describes what the page should look like for the current data, and the framework updates the DOM when the data changes. This removes a large amount of hand-written DOM code.
  • Structure: conventions for routing (which component shows for which URL), state (where shared data lives) and folders let teams work on one large code base without clashing.
  • Tooling: build steps bundle, minify and split code for fast delivery, and there are testing and debugging tools and a large community.

The difference is easiest to see side by side. Both fragments show a list of games, but only the second keeps itself up to date:

Without a framework: the developer updates the DOM by hand
function addGame(name) {
  games.push(name);
  const li = document.createElement('li');
  li.textContent = name;
  document.querySelector('#game-list').appendChild(li);   // must remember to update the page
}
With a framework (Vue-style template, illustrative)
<ul>
  <li v-for="game in games">{{ game }}</li>      <!-- the framework redraws when games changes -->
</ul>

The costs are real: a learning curve, extra code to download (which slows loading), a build process, and dependence on a project that must be kept up to date.

Template Engines and CSS Frameworks

Template engines allow developers to inject dynamic data into HTML templates on the server before sending the page to the client, avoiding duplicate HTML markup. Template engines support variables, control structures (loops, conditionals), and template inheritance.

A worked template example uses Jinja2, the template engine used by Flask. The template is one HTML layout with placeholders; the Python code supplies the data.

Python: filling a template with data
from jinja2 import Template

page = Template("""<ul>
{% for g in games %}  <li>{{ g.name }} - ${{ "%.2f"|format(g.cost) }}{% if g.cost > 40 %} (premium){% endif %}</li>
{% endfor %}</ul>""")

print(page.render(games=[{"name": "Kelp Quest", "cost": 20},
                         {"name": "Star Sailor", "cost": 45}]))
Output
<ul>
  <li>Kelp Quest - $20.00</li>
  <li>Star Sailor - $45.00 (premium)</li>
</ul>

The {% %} blocks are control structures (a loop and a condition) and {{ }} inserts a value. Because the layout is written once, the header and navigation can be shared by every page through template inheritance. Flask switches on escaping for its HTML templates (the plain Template class above does not), so a value such as <script> is displayed rather than run, which links this section to cross-site scripting.

CSS frameworks provide pre-built components and responsive utility classes to accelerate styling and ensure consistent design across pages. They typically include grid systems, responsive breakpoints, and pre-styled UI components.

Predesigned CSS classes work the other way: you write almost no CSS and instead add ready-made class names to the HTML.

HTML: Bootstrap-style predesigned classes (illustrative)
<div class="container">
  <div class="row">
    <div class="col-12 col-md-4"><button class="btn btn-primary">Buy</button></div>
  </div>
</div>

Here container, row and col-* make a responsive grid (a full-width column on phones, one third of the row from medium screens), and btn btn-primary gives a styled button. The trade-off is that sites built with the same framework can look alike, and the whole stylesheet is downloaded even if only a few classes are used.

Open-Source Software

🎯 (SE-12-05)

📌 Explain the use and development of open-source software in relation to web development

Much of the modern web is built on open-source software. Web servers (Apache, Nginx), programming languages (Python, Node.js), frameworks (React, Django), and databases (PostgreSQL, MySQL) are all open source. The NPM (Node Package Manager) ecosystem alone hosts millions of open-source packages that developers can import with a single command (npm install package-name).

"Open source" means the source code is published under a licence that lets others read, use, modify and share it. It is not the same as "free of charge" (many open-source products are sold as services), and it is not the same as "public domain": the author still holds the copyright, and the licence is what grants the permissions. In Australia the licence works because of the Copyright Act 1968, which gives the author exclusive rights that the licence then shares on stated conditions.

How open-source software is developed

  1. A maintainer publishes the code in a public repository with a licence, a README and instructions for contributing.
  2. Users report bugs and suggest features as issues.
  3. A contributor forks (copies) the repository, creates a branch, makes a change, and opens a pull request back to the original.
  4. Maintainers and other contributors review the change, request edits, and merge it if it meets the project's standards and tests.
  5. New versions are released, and users update their dependencies.

This is the same Git workflow as the version-control section, applied across a community. The benefits are low cost, many reviewers, fast fixes and no lock-in to one supplier. The costs are uneven quality, projects that are abandoned, and the fact that a bug in a popular component affects everyone who uses it. The Heartbleed flaw of 2014, a bug in the widely used OpenSSL library, is a documented example of both: a large share of the web's servers depended on one small project.

Security dependency risk and managing dependencies

Relying on open-source libraries introduces a supply chain security risk: if a maintainer introduces a vulnerability (accidentally or maliciously), every project that depends on it is affected. Engineers should regularly check for known vulnerabilities in dependencies, update promptly, and include only libraries with active maintenance and community trust.

  • npm audit compares the installed versions against a database of known vulnerabilities; running it regularly, and updating, is the practical defence against supply-chain risk.

Managing Load Times

🎯 (SE-12-07, SE-12-08)

📌 Investigate methods to support and manage the load times of web pages/applications

Minification & Compression

Minification removes whitespace, comments, and unused code from HTML/CSS/JS files, reducing file size. GZIP/Brotli compression further compresses files before transmission — the server compresses the file, the browser decompresses it. Text files such as HTML, CSS and JavaScript compress very well, often to a fraction of their original size.

Caching

HTTP Cache-Control headers instruct the browser to store static assets (images, CSS, JS) locally for a defined period. On repeat visits, cached files load instantly without a server request. Service workers in PWAs enable advanced programmatic caching strategies.

Content Delivery Networks (CDN)

A CDN distributes static assets across servers in multiple geographic locations. Users receive files from the nearest server, reducing latency. Popular CDNs include Cloudflare, AWS CloudFront, and Fastly.

Lazy Loading

Images and heavy components are only loaded when they enter the user's viewport, rather than all at once on page load. Implemented with the loading="lazy" HTML attribute or JavaScript Intersection Observer API. Significantly reduces initial page weight.

Code Splitting

Bundlers (Webpack, Vite) split a large JavaScript application into smaller chunks that are only loaded when needed. A user visiting the home page doesn't need to download the JavaScript for the account settings page until they navigate there.

Core Web Vitals

Google's set of real-world performance metrics: LCP (Largest Contentful Paint — how fast main content loads), INP (Interaction to Next Paint — responsiveness), and CLS (Cumulative Layout Shift — visual stability). Google uses them as one of many signals in search ranking.

Scenario A school news site loads slowly on a phone. Lighthouse shows three 4 MB photos. Resizing and compressing them to WebP (about 300 KB each), adding loading="lazy" to images below the fold and turning on caching cuts the data for a first load from about 12 MB to about 1 MB, and repeat visits reuse the cached files. The worked example below shows the arithmetic.

Web Content Management Systems

🎯 (SE-12-06)

📌 Research, experiment with and evaluate the prevalence and use of web content management systems (CMS)

A Content Management System (CMS) is a software platform that allows users to create, edit, organise, and publish digital content via a graphical interface — without requiring direct coding knowledge. CMSs run a very large share of the websites on the internet (W3Techs publishes the current figures), and WordPress alone is used by a large share of all sites.

What a CMS is made of

  • Content store: a database holding pages, posts, users and settings, separate from the design.
  • Admin interface: forms and an editor so non-programmers can write, review and publish.
  • Templates or themes: the code that turns stored content into HTML pages, so changing the theme restyles the whole site.
  • Plugins or extensions: add-ons for features such as forms, shops and SEO, written by third parties.
  • Roles and workflow: permissions (author, editor, administrator) and drafts, so an article can be reviewed before it goes live.

The separation of content from presentation is the key idea, and it explains the headless variant below: once content is stored separately, any front end can display it.

CMS Type Examples Evaluation
Traditional (Coupled) WordPress, Drupal, Joomla Pros: All-in-one, large plugin ecosystem, easy for non-developers. Cons: Tightly coupled front-end limits design flexibility; common target for security exploits due to widespread use.
Headless CMS Contentful, Sanity, Strapi Pros: Content served via API to any front-end (web, mobile, IoT); maximum design flexibility; better performance. Cons: Requires developer to build the front-end separately; higher initial complexity.
Visual / No-Code Webflow, Squarespace, Wix Pros: Drag-and-drop interface; fast deployment; hosted infrastructure included. Cons: Limited customisation; vendor lock-in; less suited for complex custom functionality.

The Contribution of Back-End Development

🎯 (SE-12-07)

📌 Assess the contribution of back-end web development to the success of a web application

Back-end development is responsible for all logic that occurs on the server — the invisible engine that powers every user-facing feature. Its contribution to project success encompasses several critical dimensions:

Technology Selection

The choice of back-end framework determines the project's scalability, maintainability, and development speed. Django (Python) provides a "batteries-included" approach with an ORM, admin panel, and authentication built in — accelerating development of data-heavy applications. Node.js/Express enables the same language (JavaScript) on front-end and back-end, simplifying the development team's skill requirements. Flask offers a minimal, flexible microframework for APIs. The right technology choice directly impacts delivery timelines and long-term maintenance cost.

Business Logic and Data Integrity

The back end enforces all business rules that protect data integrity. For example, validating that a user's age is above 18 before processing a purchase, calculating order totals including applicable tax rates, or checking inventory levels before confirming a stock reservation. Enforcing these rules on the server (rather than only client-side) is essential because client-side code can be bypassed by malicious users using browser developer tools.

Security Enforcement

The back end is the primary security boundary of a web application. It implements authentication (password hashing with bcrypt, JWT token management), authorisation (role-based access control), input sanitisation (preventing SQL injection and XSS), and rate limiting (preventing brute-force login attacks). A poorly secured back end exposes the entire database and all user data to attackers.

To assess a contribution is to judge how much it matters and why. A useful way to organise that judgement is to test the back end against criteria that a web application is measured by, and to give evidence for each.

CriterionBack-end contributionWhat happens if it is weak
SecurityPassword hashing, sessions, role checks, parameterised queries, output encoding, rate limitingAccounts taken over, data stolen, site defaced
Correctness and integrityServer-side validation and business rules; transactions that succeed or fail as a wholeWrong totals, oversold stock, corrupt records
PerformanceEfficient queries, indexes, caching, sending only the data neededSlow pages and timeouts under load
ScalabilityStateless handlers, shared session store, load balancing, a database that can growThe site fails when it becomes popular

Worked example: enforcing a rule on the server

The browser's form might limit the quantity box to 1 to 5, but anyone can send a request with any value. The back end applies the rule again and answers with a status code that says what was wrong:

Python: server-side validation of an order quantity
def validate_order(quantity_text, stock):
    if not quantity_text.isdigit():
        return (400, "Quantity must be a whole number")
    quantity = int(quantity_text)
    if quantity < 1:
        return (400, "Quantity must be at least 1")
    if quantity > stock:
        return (409, f"Only {stock} in stock")
    return (200, f"Order accepted: {quantity}")

for text in ["2", "0", "abc", "-1", "9"]:
    print(repr(text), validate_order(text, 5))
Output

Notice that "-1" is caught by the first test, because the minus sign is not a digit. Testing with awkward inputs like this is how you find gaps. Status 409 (Conflict) tells the client the request was valid but cannot be done in the current state.

Worked example: efficiency is a back-end matter too

Slow pages are often caused by too many database queries. The first version below asks one question per publisher; the second asks once. On the running database the loop needs four queries (one for the publishers and one for each of the three), and with 1,000 publishers it would need 1,001. The join needs one however many there are.

Python: many small queries against one grouped query
# Slow: 1 query for the publishers, then 1 more for each publisher (the "N + 1" pattern)
for pub_id, name in db.execute("SELECT Publisher_ID, Name FROM Publishers").fetchall():
    titles = db.execute("SELECT Name FROM Games WHERE Publisher_ID = ?", (pub_id,)).fetchall()
    print(name, len(titles))

# Better: one query does the counting
sql = """SELECT Publishers.Name, COUNT(Games.ID)
         FROM Publishers JOIN Games ON Games.Publisher_ID = Publishers.Publisher_ID
         GROUP BY Publishers.Name"""
for name, total in db.execute(sql):
    print(name, total)

Making the judgement

A strong assessment weighs the back end against the other parts. A back end that is secure, correct and quick gives users a site they can trust, so its contribution to success is large. But it cannot rescue a confusing interface or a slow front end (an oversized image is a front-end problem), and a well-built site still fails if the business idea does not work. So the judgement is that the back end is essential and often decisive for trust, data integrity and scalability, but it is one of several contributors, and it is most visible when it fails.

The Back-End Web Request Process

The Request-Response Lifecycle

Web Server SoftwareSoftware such as Nginx or Apache receives the raw HTTP request and routes it to the correct application handler. Nginx is also used as a reverse proxy and for serving static files efficiently.
Web FrameworkThe framework (e.g., Flask, Django, Express) parses the request URL and HTTP method, matches it against defined routes, and calls the appropriate handler function (view/controller).
ObjectsThe framework provides Request and Response objects — structured wrappers around the raw HTTP data. The Request object gives access to headers, query parameters, form data, and cookies; the Response object is used to construct the reply.
LibrariesThe handler uses imported libraries to perform specialised tasks — authentication libraries (e.g., Passport.js), email sending libraries (e.g., Nodemailer), file handling, or cryptographic operations.
DatabasesThe handler queries the database (via raw SQL or ORM) to retrieve, insert, update, or delete records. The database returns results which the handler uses to construct the response payload (JSON or rendered HTML).
Full Request Lifecycle Browser → DNS → Web Server (Nginx) → Framework Router → Handler Function → Library Calls → Database Query → Data returned → Handler builds Response → JSON/HTML sent back → Browser renders result.

Worked example: a Flask route from URL to response

Flask is a small Python web framework. This program (illustrative, using the GameShelf database created in the SQL section) shows each element of the dot point in one place: the framework, its request and response objects, a library, and the database.

Python (Flask): two routes for GameShelf
import sqlite3
from flask import Flask, jsonify, request, abort, render_template_string

app = Flask(__name__)                          # the web framework object

def get_db():
    db = sqlite3.connect("gameshelf.db")       # library: Python's built-in sqlite3
    db.row_factory = sqlite3.Row               # rows behave like dictionaries
    return db

@app.route("/games")                           # route: this URL pattern -> this function
def list_games():
    max_cost = request.args.get("max_cost", type=float)    # Request object: the ?max_cost=30 part
    if max_cost is None:
        abort(400, description="max_cost must be a number")
    db = get_db()
    rows = db.execute(
        "SELECT Name, Cost FROM Games WHERE Cost <= ? ORDER BY Cost ASC",
        (max_cost,),                           # the ? placeholder keeps data separate from the SQL
    ).fetchall()
    db.close()
    return jsonify([dict(r) for r in rows])    # Response object: JSON body, status 200

@app.route("/games/<int:game_id>")             # <int:game_id> captures the number from the URL
def show_game(game_id):
    db = get_db()
    row = db.execute("SELECT Name, Cost FROM Games WHERE ID = ?", (game_id,)).fetchone()
    db.close()
    if row is None:
        abort(404)                             # no such game: send 404 Not Found
    return render_template_string("<h1>{{ name }}</h1><p>${{ '%.2f' % cost }}</p>",
                                  name=row["Name"], cost=row["Cost"])

for line in errors:
    print(line)

Incorporating GROUP BY

GROUP BY collapses the rows that share a value into one row per group, and functions such as SUM, AVG, COUNT, MAX and MIN calculate one value for each group. Reading the query below: find each game's publisher, group the games by publisher, then for each group count the games, average the cost and find the dearest.

       AVG(Games.Cost) AS AvgCost, MAX(Games.Cost) AS Dearest
FROM Games, Publishers
WHERE Publishers.Publisher_ID = Games.Publisher_ID
GROUP BY Publishers.Publisher_ID
ORDER BY Titles DESC

Comparing ORM to SQL

🎯 (SE-12-06, SE-12-08)

📌 Compare Object-Relational Mapping (ORM) to SQL

Method Description Pros & Cons
🛠️ Raw SQL Queries written directly in SQL and sent to the database engine. Provides fine-grained control over every aspect of the query. Pros: Maximum performance; expressive power for complex JOINs, subqueries, and aggregations; universal — works with any SQL database.
Cons: Vulnerable to SQL injection if inputs aren't parameterised; verbose for simple CRUD operations; query strings are hard to refactor.
🛠️ ORM Maps database tables to Python/JavaScript classes. Developers interact with objects; the ORM generates SQL automatically (e.g., Django ORM, SQLAlchemy, Sequelize). Pros: Faster development for standard operations; built-in input sanitisation prevents injection; database-agnostic (swap PostgreSQL for MySQL with minimal changes); code is more readable and object-oriented.
Cons: Can generate inefficient SQL for complex queries; adds an abstraction layer that obscures what is actually executed; requires learning the ORM API on top of SQL.

What an ORM maps

The Course Specifications describe an ORM as a layer of abstraction between the database and the programming language: in an object-oriented language, database rows are represented as objects and their columns as properties of the object. Students are expected to interpret code fragments used in an ORM framework, so the goal here is to read ORM code fluently, not to memorise one library.

Worked example: the running database as classes

This code uses SQLAlchemy, a widely used Python ORM (installed with pip install sqlalchemy). It describes the same three tables that setup_db.py created. Each class is one table; each attribute line is one column; ForeignKey and relationship describe the links.

Python (SQLAlchemy): models.py
from sqlalchemy import create_engine, ForeignKey, select, func
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column, relationship, Session

class Base(DeclarativeBase):
    pass

class Publisher(Base):
    __tablename__ = "Publishers"                     # the class maps to this table
    Publisher_ID: Mapped[int] = mapped_column(primary_key=True)
    Name: Mapped[str]
    games: Mapped[list["Game"]] = relationship(back_populates="publisher")

class Developer(Base):
    __tablename__ = "Developers"
    Developer_ID: Mapped[int] = mapped_column(primary_key=True)
    First_name: Mapped[str]
    Last_name: Mapped[str]
    games: Mapped[list["Game"]] = relationship(back_populates="developer")

class Game(Base):
    __tablename__ = "Games"
    ID: Mapped[int] = mapped_column(primary_key=True)
    Name: Mapped[str]                                # each attribute maps to a column
    Release_date: Mapped[str]
    Cost: Mapped[float]
    Publisher_ID: Mapped[int] = mapped_column(ForeignKey("Publishers.Publisher_ID"))
    Developer_ID: Mapped[int] = mapped_column(ForeignKey("Developers.Developer_ID"))
    publisher: Mapped[Publisher] = relationship(back_populates="games")
    developer: Mapped[Developer] = relationship(back_populates="games")

engine = create_engine("sqlite:///gameshelf.db")

from models import *

with Session(engine) as session:
    query = select(Game).where(Game.Cost > 30).order_by(Game.Name)

The query object is built in Python, but the ORM turns it into SQL for you. It sends something equivalent to SELECT ... FROM Games WHERE Games.Cost > ? ORDER BY Games.Name, with the value 30 passed separately, which is also why an ORM protects against SQL injection by default. Reading a game's developer makes a further query for that developer.

The Specifications' grouping example (each developer's total for 'Games Inc') is written like this. The join calls replace the matching conditions in WHERE, and group_by, order_by and func.sum correspond directly to GROUP BY, ORDER BY and SUM:

Python (SQLAlchemy): the GROUP BY query
from models import *

with Session(engine) as session:
    query = (
        select(Developer.First_name, Developer.Last_name, func.sum(Game.Cost).label("Totalcost"))
        .join(Game).join(Publisher)
        .where(Publisher.Name == "Games Inc")
        .group_by(Developer.Developer_ID)
        .order_by(Developer.Last_name.desc())
    )
    for row in session.execute(query):
        print(row.First_name, row.Last_name, row.Totalcost)

Front-End and Back-End Collaboration

API Contracts and Documentation

The primary collaboration mechanism between front-end and back-end developers is the API contract — an agreed-upon specification of every endpoint's URL, HTTP method, request parameters, and response format. Tools like OpenAPI/Swagger allow teams to document and even mock APIs before the back end is fully built, enabling front-end and back-end development to proceed simultaneously. This prevents integration errors at the end of the project and enables both teams to work independently with confidence.

Worked example: an API contract

Before either team writes code, they agree on the contract. This fragment (in the OpenAPI format, which is widely used to document web APIs) says that GET /games needs a numeric max_cost and returns a list of objects with a name and a cost:

OpenAPI (YAML): the agreed contract for one endpoint
openapi: 3.0.3
info: { title: GameShelf API, version: "1.0" }
paths:
  /games:
    get:
      summary: List games costing no more than max_cost
      parameters:
        - { name: max_cost, in: query, required: true, schema: { type: number } }
      responses:
        "200":
          description: A list of games
          content:
            application/json:
              schema:
                type: array
                items:
                  type: object
                  properties:
                    Name: { type: string }
                    Cost: { type: number }
        "400":
          description: max_cost is missing or not a number

With the contract written down, the front-end developer can build against fake data that has the agreed shape (a small mock that returns [{ Name: 'Kelp Quest', Cost: 20 }] is enough), and swap in the real API later.

Meanwhile the back-end developer writes a contract test that fails if the real API drifts from the agreement:

Python: a contract test (runs with pytest or as a plain function)
def test_games_contract(client):
    response = client.get("/games?max_cost=30")
    assert response.status_code == 200
    for game in response.get_json():
        assert set(game) == {"Name", "Cost"}                 # exactly the agreed fields
        assert isinstance(game["Cost"], (int, float))

Run against the GameShelf route, the test passes silently. Now suppose the back-end developer renames Cost to Price without telling anyone. Without the test, the front end fails in users' browsers with a message like Cannot read properties of undefined (reading 'toFixed'). With it, the change fails the test in seconds, before it is merged. The fix is a conversation: either revert the rename, or agree on a new version of the contract (for example /v2/games) and change both sides together.

Version Control and Branching Strategies

Teams use Git branching workflows to manage parallel development. In the Git Flow model: the main branch always contains production-ready code; develop is the integration branch for completed features; and individual feature/ branches are created for each task. Pull Requests (PRs) are submitted when a feature is complete — requiring at least one peer code review before merging. This enforces code quality and knowledge sharing across the team, and ensures no one developer is a single point of failure for any part of the system.

Open-Source and Ethical Collaboration

Collaborative web development carries ethical responsibilities. Teams must fairly attribute contributions, respect the licences of all third-party code used, ensure equitable division of workload, and maintain transparent communication with stakeholders about progress and setbacks. When using open-source code libraries, teams must monitor for security vulnerabilities and update dependencies promptly to protect users.

Designing a Progressive Web App

🎯 (SE-12-02, SE-12-03, SE-12-06)

📌 Design, develop and implement a progressive web app (PWA)

  • the application of design and user interface (UI) and user experience (UX) principles of font, colour, audio, video and navigation
  • a UI that considers accessibility and inclusivity

UI and UX Principles

Typography

Select legible, web-safe or Google Fonts typefaces. Establish a clear typographic hierarchy (H1 → H2 → body → caption). Minimum body font size of 16px for readability. Sufficient line-height (1.5–1.7) for comfortable reading. Limit typeface count to 2 maximum.

Colour

Use a defined colour palette: primary, secondary, and accent colours plus semantic colours (danger red, success green). Ensure a minimum WCAG AA contrast ratio of 4.5:1 between text and background. Avoid conveying information by colour alone (for colour-blind users).

Audio and Video

Provide controls for all auto-playing media. Supply captions/subtitles for video content (WCAG requirement). Compress media for fast loading. Avoid content that flashes more than 3 times per second (seizure risk).

Navigation

Consistent navigation structure across all views. Clear visual indication of the current page (active state). Breadcrumbs for deep navigation hierarchies. Touch-friendly tap targets (minimum 44×44px). Logical tab order for keyboard navigation.

5-Point Syllabus Compliance Checklist for PWA UX

Ensure your software engineering project meets these core NESA user experience standards:

  1. Responsiveness: Adapts cleanly to mobile, tablet, and desktop viewports.
  2. Accessibility: Achieves WCAG AA contrast and full keyboard operability.
  3. Offline Grace: Displays a custom UI (via Service Worker) when the network drops, rather than the browser's default error.
  4. Installability: Provides a valid manifest.json so the app can be pinned to the home screen.
  5. Consistency: Uses a predictable interaction model and uniform colour palette across all screens.

Accessibility and Inclusivity

PWA interfaces must be designed to be usable by everyone, including people with visual, auditory, cognitive, or motor disabilities:

Semantic HTMLUse correct elements for their purpose (<button> for buttons, <nav> for navigation, <main> for content). Screen readers rely on semantic structure to describe pages to blind users.
Alt TextEvery non-decorative image must have descriptive alt attribute text. Decorative images use alt="" so screen readers skip them.
⌨️ Keyboard NavigationAll interactive elements must be reachable and operable using only a keyboard (Tab to focus, Enter to activate). Required for users who cannot use a mouse.
ARIA AttributesARIA (Accessible Rich Internet Applications) attributes (e.g., aria-label, aria-expanded, role) describe the state and purpose of dynamic UI components to assistive technologies.
Focus ManagementWhen a modal or dialog opens, keyboard focus must move into it. When it closes, focus returns to the triggering element. This ensures keyboard users don't lose their place in the interface.

Core PWA Technical Requirements

Web App Manifest

A JSON file (manifest.json) that defines the app's name, icons, theme colour, and display mode (fullscreen/standalone). Enables the "Add to Home Screen" install prompt in mobile browsers.

Service Worker

A JavaScript file that runs in the background as a network proxy. Intercepts fetch requests to serve cached assets when offline, enable push notifications, and implement background sync for reliable data submission.

HTTPS Required

PWAs must be served over HTTPS — service workers are restricted to secure origins. HTTPS also builds user trust and is a requirement for browser installability.

JavaScript — Service Worker: Offline Cache Strategy
const CACHE_NAME = 'pwa-cache-v1';
const ASSETS_TO_CACHE = ['/', '/index.html', '/css/styles.css', '/js/app.js'];

// Install event: cache core app shell assets
self.addEventListener('install', event => {
    event.waitUntil(
        caches.open(CACHE_NAME).then(cache => cache.addAll(ASSETS_TO_CACHE))
    );
});

// Fetch event: serve from cache, fallback to network
self.addEventListener('fetch', event => {
    event.respondWith(
        caches.match(event.request).then(cached => cached || fetch(event.request))
    );
});

The service worker lifecycle

A service worker is a script the browser runs separately from the page. It has its own lifecycle, and most PWA bugs come from misunderstanding it.

  1. Register. The page asks the browser to install the worker (code below). The browser downloads sw.js.
  2. Install. The worker's install event runs once for each new version. It normally caches the app shell here.
  3. Activate. When the new worker takes over, the activate event runs. This is the place to delete old caches.
  4. Fetch. From now on, every request from pages the worker controls goes through its fetch event, where it decides whether to answer from the cache or the network.
JavaScript (in the page): register the worker
if ('serviceWorker' in navigator) {
  window.addEventListener('load', () => {
    navigator.serviceWorker.register('/sw.js')
      .then(reg => console.log('Service worker registered, scope:', reg.scope))
      .catch(err => console.log('Registration failed:', err));
  });
}

On a first visit the console shows Service worker registered, scope: https://…/. The worker controls pages only inside its scope (the folder it is served from), so sw.js is placed at the site root. A page loaded before the worker was installed is not controlled until it is reloaded.

Caching strategies

StrategyHow it worksBest forDrawback
Cache firstAnswer from the cache; use the network only if it is not cachedThe app shell, fonts, images and other files that rarely changeUsers may see stale files until the cache version changes
Network firstTry the network; use the cache if the network failsData that changes often, such as headlines or pricesSlower when the connection is poor
Stale while revalidateAnswer from the cache immediately, fetch a fresh copy in the background for next timeContent where a slightly old copy is acceptable, such as avatarsThe first view after a change is one version behind

The earlier example is purely cache first. A more realistic worker uses network first for the API, cache first for the shell, cleans old caches when the version changes, and shows a friendly offline page instead of the browser's error:

JavaScript: sw.js with versioned cache, two strategies and an offline page
const CACHE = 'gameshelf-v2';                                  // change this to release new files
const SHELL = ['/', '/index.html', '/css/site.css', '/js/app.js', '/offline.html'];

self.addEventListener('install', event => {
  event.waitUntil(caches.open(CACHE).then(cache => cache.addAll(SHELL)));
});

self.addEventListener('activate', event => {                   // delete caches from old versions
  event.waitUntil(
    caches.keys().then(names => Promise.all(
      names.filter(name => name !== CACHE).map(name => caches.delete(name))
    ))
  );
});

self.addEventListener('fetch', event => {
  const url = new URL(event.request.url);
  if (url.pathname.startsWith('/games')) {                     // API data: network first
    event.respondWith(
      fetch(event.request).catch(() => caches.match(event.request))
    );
  } else {                                                     // everything else: cache first
    event.respondWith(
      caches.match(event.request).then(cached =>
        cached || fetch(event.request).catch(() => caches.match('/offline.html')))
    );
  }
});

Testing that it really works offline

  1. Serve the app over HTTPS (or from localhost, which browsers treat as secure for development) and load it once.
  2. Open the dev tools, Application panel, Service Workers. You should see sw.js listed as activated and running. Under Cache Storage you should see gameshelf-v2 containing the shell files.
  3. Tick Offline (or switch off the computer's Wi-Fi) and reload. Expected result: the app shell still loads instantly; the list of games comes from the network-first fallback if you have loaded it before, or the offline page appears if you have not.
  4. Change CACHE to gameshelf-v3, reload twice, and check Cache Storage: the old gameshelf-v2 cache is deleted after the new worker activates.
  5. Run Lighthouse and read the installability and PWA checks it reports; fix anything it lists, such as a missing icon size or a manifest without a start_url.

Browsers decide for themselves when to offer installation. The usual conditions are a secure connection, a linked manifest with a name, icons and a start URL, and (in some browsers) a registered service worker, so check the current requirements for the browsers you support rather than assuming them.

Worked example: accessible, inclusive markup

Accessibility is built into the markup, not added afterwards. This fragment gives a form a visible label, a status message announced by screen readers and a landmark structure for navigation:

HTML: labelled form, announced status and landmarks
<header>
  <nav aria-label="Main">
    <a href="/" aria-current="page">Home</a>
    <a href="/games">Games</a>
  </nav>
</header>
<main>
  <h1>Find a game</h1>
  <form>
    <label for="max">Maximum price (AUD)</label>
    <input id="max" name="max" type="number" min="0" inputmode="decimal" required>
    <button type="submit">Search</button>
  </form>
  <p id="status" role="status">3 games found.</p>   <!-- read out when its text changes -->
</main>
  • The label is tied to the input with for and id, so a screen reader announces "Maximum price" and a tap on the label focuses the box.
  • Real button, nav and main elements give keyboard focus, key handling and navigation landmarks for free; a clickable div would need all of that added by hand.
  • role="status" makes a screen reader announce a change to the message without moving focus.

Exam tip: "Design, develop and implement" a PWA NESA's 2025 online paper compared a PWA with an interactive website for a weather-app scenario (one published exam). A strong answer names what makes an app progressive (a manifest for installation, a service worker for offline use, HTTPS), says which strategy the worker uses for which files and why, and ties the choice to the scenario: weather data should use network first, because a cached forecast can mislead, while the app shell can be cache first. For UI and UX questions, tie each principle to a user need: contrast for low-vision users, captions for deaf users, keyboard navigation for people who cannot use a mouse, and consistent navigation for everyone. Explain trade-offs rather than only stating rules: a PWA has one code base, but fewer device features than a native app.
