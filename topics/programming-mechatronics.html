Why this matters now

Drones delivering parcels, robotic vacuum cleaners mapping your lounge room, self-driving cars trialling on real roads and prosthetic hands controlled by muscle signals: mechatronics is where software meets the physical world. Here a bug is not just an error message, it can be a robot arm moving the wrong way or a sensor reading that crashes a drone.

In this topic you will study the syllabus content on sensors, actuators and end effectors, microcontroller code, control algorithms, power and wiring, and how software manages real-time interactions.

Keep this question in mind How do you write code you can trust when it controls something that moves?

Applications of Mechatronic Systems

🎯 (SE-11-03)

📌 Outline applications of mechatronic systems in a variety of specialised fields

Mechatronics combines mechanical engineering, electronics and computing so that a machine can sense its surroundings, decide what to do and act on the decision. Every application below follows the same loop: sensors measure something, a controller running a program decides, and actuators change the physical world. Only the sensors, the actuators and the rules differ from field to field.

AerospaceUnmanned Aerial Vehicles (UAVs) use mechatronics for flight stabilisation, GPS navigation, and autonomous landing routines.
HealthcareAdvanced prosthetics use electromyography (EMG) sensors to detect muscle signals, allowing users to control bionic limbs with high precision.
AutomotiveModern vehicles incorporate mechatronic subsystems such as Anti-lock Braking Systems (ABS) and Electronic Stability Control (ESC) to enhance driver safety.
MiningAutonomous haul trucks and drills, used at some Australian mines, follow programmed routes using GPS and other sensors so that fewer people work near hazards.
ManufacturingIndustrial robot arms weld, paint and assemble parts, repeating the same motion accurately for a whole shift.
AgricultureAutomatic milking systems, irrigation controllers and guided tractors sense the animal, the soil or the paddock and adjust what they do.

Why use a mechatronic system, and what does it cost?

  • Benefits: consistent repeatable results, work in places that are dangerous or remote, continuous operation, and fine control that a person cannot match (a drone corrects its balance many times a second).
  • Trade-offs: higher up-front cost, specialist skills to design and repair, new failure modes (a sensor fault or software bug can make the machine act wrongly), safety risks where machines share space with people, and changes to the jobs people do.
Exam tip: "Outline" an application An outline answer is brief and specific. Naming a real sensor and a real actuator earns more than a general statement such as "robots make farming easier".

Hardware Requirements and Code Development

🎯 (SE-11-01, SE-11-03)

📌 Identify the hardware requirements to run a program and the effect on code development

  • assessing the relationship of microcontrollers and the central processing unit (CPU)
  • the influence of instruction set and opcodes
  • the use of address and data registers

Microcontrollers and the CPU

The central processing unit (CPU) is the part of a computer that fetches and executes instructions. A microcontroller is a whole small computer on one chip: a CPU core plus flash memory (holds the program), RAM (holds variables while running) and peripherals such as GPIO pins, analog-to-digital converters (ADCs) and PWM outputs. A microprocessor is mainly the CPU, so a computer built around one needs separate RAM, storage and input/output chips. Single-board computers such as the Raspberry Pi put a microprocessor, memory and ports on one board and run a full operating system. The CPU is therefore a part of a microcontroller, and the microcontroller is what most mechatronic systems are built around.

Many systems use both: a microprocessor for vision and planning, and a microcontroller for the fast, safety-critical motor loop.

Effect on code development

  • Memory limits data choices. With 2 KB of RAM you cannot store a long list of readings or load a large library.
  • Word size affects arithmetic. On an Uno an int is 16 bits, so it overflows past 32 767; counting milliseconds needs a larger type. The 32-bit Pico does not have this problem at that scale.
  • Small chips may lack floating-point hardware, so decimal maths is done in software and is slow; integers are faster. Code is also built for one instruction set: a program compiled for AVR will not run on Arm.
  • Language trades speed for convenience. Compiled C++ is fast and compact; MicroPython is quicker to write but needs more memory and runs slower.
  • Voltage and pins matter. A Pico's pins are 3.3 V and must not be driven at 5 V; an Uno's pins are 5 V. The number of ADC and PWM pins limits how many sensors and motors you can connect.

Instruction set and opcodes

A CPU repeats the fetch, decode, execute cycle: fetch the next instruction from memory, decode which operation it asks for, then execute it. The instruction set is the complete list of operations a particular CPU understands. Each machine instruction holds an opcode (which operation) and its operands (which registers, addresses or values to use). A compiler or interpreter translates your Python or C++ into these instructions, so the instruction set decides what is fast, what is slow and what code can run at all. AVR and Arm are two instruction set families; RISC-V is a third.

Address and data registers

Registers are the CPU's own tiny, very fast storage. Data registers hold the values being worked on, such as a sensor reading waiting to be compared. Address registers hold the address of a memory location to read or write (the memory address register, MAR). The program counter is a special register holding the address of the next instruction, and the instruction register holds the instruction being decoded. An address is the number that identifies one memory location; the address bus carries it and the data bus carries the value. A 16-bit address can identify 216 = 65 536 locations.

Sensors, Actuators and End Effectors

🎯 (SE-11-06)

📌 Identify and describe a range of sensors, actuators and end effectors/manipulators within existing mechatronic systems

  • motion sensors
  • light level sensors
  • hydraulic actuators
  • robotic grippers

A sensor converts a physical quantity (light, heat, movement) into an electrical signal the controller can read. An actuator converts an electrical signal, plus a source of power, into physical action. An end effector is the tool at the end of a robot arm that touches the work; the arm and joints that position it are the manipulator.

Sensors (Inputs)

Devices that convert physical properties into electrical signals.

  • Motion: PIR (Passive Infrared) sensors detect the change in infrared radiation as a warm body moves across their field of view.
  • Light: LDRs (Light Dependent Resistors) change resistance based on ambient light levels.

Actuators (Outputs)

Components that convert electrical energy into physical motion.

  • Hydraulic: Utilise pressurised fluid to generate high force (e.g., in excavators).
  • Electric: DC motors or Servos that provide rotational movement.

Manipulators

The parts of the system that physically interact with objects.

  • Robotic Gripper: An end effector designed to grasp and release objects.
  • Degrees of Freedom: The number of independent movements a robot can make (see the next sections).

Motion sensors

"Motion" covers several measurements. A PIR sensor gives a digital HIGH when it sees a warm body moving, but cannot say how far away it is. An ultrasonic sensor times the echo of a sound pulse to find distance. An accelerometer or gyroscope (often together in an inertial measurement unit, IMU) reports acceleration and rotation, so a drone can tell it is tilting. A rotary encoder counts pulses as a shaft turns, giving speed and position.

Light level sensors

An LDR's resistance falls as light increases. A microcontroller cannot read resistance directly, so the LDR is wired with a fixed resistor as a voltage divider and the resulting voltage is read by an ADC. A photodiode responds faster, and a digital lux sensor sends a calibrated reading over a serial bus.

MicroPython — Sensing and Moving
from machine import Pin, PWM
import utime

sensor = Pin(14, Pin.IN)         # PIR motion sensor: 1 = movement
servo = PWM(Pin(15), freq=50)    # Actuator: a servo needs a 50 Hz signal

while True:
    if sensor.value() == 1:
        servo.duty_u16(5000)     # about a 1.5 ms pulse: move to the centre position
    else:
        servo.duty_u16(2000)     # about a 0.6 ms pulse: return to the home position
    utime.sleep(0.1)

    utime.sleep(0.5)

Hydraulic actuators

A hydraulic actuator uses an electric pump to push an incompressible liquid (oil) through valves into a cylinder, where it pushes a piston. Pressure acts equally on every surface, so force = pressure × piston area. Oil at 10 MPa (10 000 000 Pa) on a piston of area 0.005 m² gives 10 000 000 × 0.005 = 50 000 N, enough to lift several tonnes. That is why excavators and press brakes use hydraulics. The costs are a pump and hoses, oil that can leak, heat and noise, and slower, less precise control than an electric motor.

Robotic grippers

A robotic gripper is the most common end effector. A parallel-jaw gripper closes two flat fingers, an angular gripper pivots them, a vacuum gripper holds smooth flat objects with suction, and a soft gripper uses flexible fingers for fragile items such as fruit. Other end effectors include a welding torch, a paint nozzle or a 3D printer's extruder. A gripper usually has one degree of freedom (open or close), and the code limits the grip force so it does not crush the part.

Exam tip: "Identify and describe" devices For each device, give its name, what it measures or does, the kind of signal (digital or analog) or force it works with, and one system that uses it. For example: "A PIR sensor detects the infrared change caused by a moving person and outputs a digital signal; an automatic door uses it to open." Keep sensors (inputs), actuators (outputs) and end effectors (the tool) separate: a servo is an actuator, but the gripper it drives is the end effector.

Processing and diagnostic data

Mechatronic systems process raw analog signals (via ADCs) into digital data for decision-making. Diagnostic data involves monitoring internal states, such as motor temperature, battery voltage or current draw, to identify potential hardware failures before they occur. For example, a motor that suddenly draws much more current than usual may be stalled, so the program stops it before it overheats. Optimisation data is used to refine control algorithms, such as adjusting the duty cycle of a PWM signal to achieve maximum motor efficiency with minimal heat generation. Engineers use logged data to perform predictive maintenance, replacing components before a failure happens.

Analog-to-Digital Conversion (ADC)

Sensors output continuous analog voltages. Microcontrollers use Analog-to-Digital Converters to sample these voltages and convert them to digital numbers for processing. An ADC has a resolution (for example 10 or 12 bits), which sets how many levels it can represent: 2n levels for n bits.

ADC formula: count = (measured voltage ÷ reference voltage) × 2n, limited to a maximum of 2n − 1. Some textbooks use 2n − 1 as the multiplier, which changes the result by about one count.

A 10-bit ADC (1024 levels, counts 0 to 1023) with a 5 V reference measuring 2.5 V gives (2.5 ÷ 5) × 1024 = 512. One count is 5 V ÷ 1024 ≈ 4.9 mV, the smallest change the ADC can notice. Software then uses the count to make decisions, for example switching on a cooling fan when a temperature crosses a threshold.

Worked example: from raw count to a decision

A TMP36 temperature sensor outputs 10 mV per °C with 0.5 V at 0 °C. A 10-bit ADC (5 V reference) reads a count of 158. The steps are: count → volts → °C → decision.

  1. Volts = 158 × 5 ÷ 1024 = 0.771 V.
  2. Temperature = (0.771 − 0.5) × 100 ≈ 27.1 °C.
  3. 27.1 °C is above the 26 °C setpoint, so the vent should open.

Because one count is about 4.9 mV, this sensor and ADC can only resolve steps of about 0.5 °C. Logging the readings gives optimisation data:

Python — converting counts and analysing a log
VREF = 5.0
STEPS = 1024                       # 10-bit ADC

def count_to_celsius(count):
    volts = count * VREF / STEPS   # counts to volts
    return (volts - 0.5) * 100     # TMP36: 10 mV per degree, 0.5 V at 0 degrees

print(round(count_to_celsius(158), 1))

log = [(0, 24.8), (10, 26.9), (20, 29.4), (30, 28.1), (40, 26.2), (50, 25.9)]   # (minute, deg C)
hottest = max(temp for minute, temp in log)
minutes_hot = sum(10 for minute, temp in log if temp > 28)    # samples are 10 min apart
print("Peak:", hottest, "C; above 28 C for about", minutes_hot, "min")

Motion Constraints and Degrees of Freedom

Motion Constraints are limitations on how a mechanical system can move. Some come from the physical design: a joint that can only turn through a set range, a gripper that can only open and close, a differential-drive robot that can turn on the spot but cannot slide sideways. Others are added in software: a maximum speed or acceleration, and keep-out zones that the arm must not enter. Software must respect these constraints when it generates movement commands, because exceeding them can damage the mechanism, the work or a person.

Python — enforcing joint limits in software
def clamp(value, low, high):
    return max(low, min(high, value))

SHOULDER_LIMITS = (10, 170)        # degrees the joint may move through
ELBOW_LIMITS = (0, 135)

def safe_angles(shoulder, elbow):
    return clamp(shoulder, *SHOULDER_LIMITS), clamp(elbow, *ELBOW_LIMITS)

print(safe_angles(90, 45))
print(safe_angles(200, -20))
Expected output
(90, 45)
(170, 0)

Degrees of Freedom (DOF) is the number of independent movements a mechanism can make, usually one for each joint that can move on its own. A joint may rotate (revolute) or slide along a line (prismatic). More degrees of freedom let the end effector reach more positions and orientations, but each one needs an actuator, a sensor and more code.

Pan-and-tilt camera mount2Turn left or right; tilt up or down
Two-joint planar arm2Shoulder and elbow angles, which together set where the hand is on a flat surface
Six-axis industrial arm6Six joint angles, giving any position and orientation in 3D space

Combination of Subsystems

Complex mechatronic systems are built by combining simpler subsystems. For example, an automated warehouse robot combines: (1) a vision subsystem to identify items, (2) a navigation subsystem to move through the warehouse, (3) a gripper subsystem to pick items, and (4) a communication subsystem to report status. The subsystems depend on each other, so software must coordinate them safely. In the code below, the gripper only opens when the robot is stationary, and the robot only drives when the gripper is closed, so it cannot drag an open gripper through a shelf.

Python — dependencies between two subsystems
class Rover:
    def __init__(self):
        self.speed = 0
        self.gripper_open = False

    def open_gripper(self):
        if self.speed != 0:                    # dependency: only when stationary
            return "REFUSED: rover is moving"
        self.gripper_open = True
        return "gripper open"

    def drive(self, speed):
        if self.gripper_open:                  # dependency: only with the gripper closed
            return "REFUSED: gripper is open"
        self.speed = speed
        return "driving at " + str(speed)

rover = Rover()
print(rover.drive(50))
print(rover.open_gripper())
print(rover.drive(0))
print(rover.open_gripper())
print(rover.drive(50))

Experiment: finding a safe gripper speed

To experiment is to change one thing on purpose, measure the result and draw a conclusion. Suppose a gripper sometimes crushes a paper cup. A fair test changes only the closing speed and keeps everything else the same.

  1. Question and hypothesis: a slower closing speed will grip the cup without crushing it.
  2. Variables: change the closing speed (independent); measure whether the cup is held or crushed (dependent); keep the cup, the gripper and the force limit constant (controlled).
  3. Method: run each speed three times and record every result, so one odd trial does not mislead you.
  4. Conclusion: choose the fastest speed that never crushes the cup, then change the code and re-test.

Power, Battery and Material Requirements

🎯 (SE-11-03, SE-11-06)

📌 Determine power, battery and material requirements for components of a mechatronic system

Before you build, work out how much power the system needs, how long a battery will last, and what the parts should be made of. Getting this wrong leads to flat batteries, resets when motors start, or a frame that bends.

Power and current requirements

Two relationships do most of the work. Ohm's law, V = I × R, links voltage, current and resistance. Power is P = V × I. Add up the current every part draws, and find the worst case: a motor draws far more when it starts or stalls than when it runs freely.

Requirement Engineering Detail
Power & Battery Current Draw Calculation: Total system current is calculated by summing the individual component currents: Total Current (mA) = Σ(Component Current)If a microcontroller draws 50 mA, two DC motors draw 300 mA each, and an LED draws 20 mA, total = 50 + 300 + 300 + 20 = 670 mA. A 5V supply must provide at least 670 mA, and a margin of about 50% is sensible, so choose a supply rated for about 1 A.
Actuators often require separate power supplies from the controller to avoid "brownouts" (voltage drops) or component damage caused by the high current demands of motors.
Material Choice Choosing based on weight, strength, and environmental conditions.Using carbon fibre for lightweight drone frames vs steel for industrial grippers.

Estimating battery life

Battery life (hours) ≈ battery capacity (mAh) ÷ average current (mA). A 2000 mAh battery powering the 670 mA system above lasts about 2000 ÷ 670 ≈ 3 hours. In practice, allow 20–30% less, because batteries lose capacity as they age and as they get cold: 2000 × 0.75 ÷ 670 ≈ 2.2 hours. Use the average current for battery life and the peak current to size the supply and wiring.

Regulating voltage and limiting current

  • Linear regulator: steps voltage down by turning the excess into heat. Dropping 9 V to 5 V at 500 mA wastes (9 − 5) × 0.5 = 2 W, which needs a heatsink and wastes battery. A buck converter is far more efficient.
  • Current-limiting resistor: an LED that drops about 2 V on a 5 V supply at 15 mA needs R = (5 − 2) ÷ 0.015 = 200 Ω. Choose the next standard value, 220 Ω, which gives about 14 mA.
  • Safety: fit a fuse on the battery lead, check polarity before connecting (reversed power can destroy a board), keep lithium batteries away from punctures and heat, and never leave them charging unattended.

Wiring Diagrams

🎯 (SE-11-06)

📌 Develop wiring diagrams for a mechatronic system, considering data and power supply requirements

A wiring diagram shows every connection in a mechatronic system: which pin connects to which component, and how power reaches each part. Draw it before you build, and update it whenever the circuit changes. A schematic uses standard electronic symbols; a pictorial or breadboard diagram shows the parts as they look. Either works, provided every connection is labelled.

  • Data connections: label each microcontroller pin and what it does, such as D9 → servo signal or A0 ← light sensor. Say whether each pin is a digital input, digital output, PWM output or analog input.
  • Power supply: show voltage and ground for every component, and the current each supply can deliver. Give motors their own supply so they don't cause the microcontroller to brown out.
  • Standard symbols and colours: red for positive, black for ground, and other colours for signals.

The LDR row is a voltage divider: the two resistors share the supply voltage, and the voltage at the joint changes as the LDR's resistance changes, which is what the analog pin reads.

Interface details a diagram must get right

  • Common ground. Every supply and the microcontroller must share a ground, or the signals have no reference and behave randomly.
  • Logic levels. A 3.3 V board such as the Pico must not be driven with a 5 V signal. Use a level shifter or a voltage divider on signals that come from 5 V parts.
  • Pin current limits. A microcontroller pin can supply only a few tens of milliamps at most (check the datasheet). Motors, pumps and relays need a driver, such as a transistor, MOSFET or H-bridge, with their own supply.
  • Flyback diode. Motors, relays and solenoids produce a voltage spike when switched off. A diode across the coil, pointing the right way, protects the driver.
  • Pull-up resistors. A button wired between a pin and ground leaves the pin floating when open. Enabling the pin's internal pull-up, as in Pin.PULL_UP, makes it read 1 when open and 0 when pressed.

📌 Determine specialist requirements that influence the design and functions of mechatronic systems designed for people with disability

Accessibility Considerations

When designing mechatronic systems for users with disabilities, engineers must consider:

Mobility Disabilities

  • Prosthetics and Exoskeletons: Systems controlled by electromyography (muscle signals), requiring real-time sensor fusion and responsive actuation.
  • Wheelchair Automation: Systems with joystick sensitivity adjustment, voice command control, or autonomous navigation for obstacle avoidance.

Visual Impairments

  • Haptic Feedback: Vibration patterns in controllers to provide tactile information instead of visual displays.
  • Spatial Audio: Sound-based navigation cues to guide users around obstacles.
  • Obstacle Detection: Ultrasonic or infrared sensors to alert users to hazards.

Speech and Hearing Impairments

  • Visual Feedback Systems: LED indicators, screen displays for status information.
  • Sign Language Recognition: Computer vision systems to interpret sign language commands.
  • Text-Based Interfaces: Keyboard or touch input for users with speech difficulties.

Severe Mobility Limitations

  • Sip-and-Puff Control: Systems activated by gentle air pressure from the mouth for users with very limited mobility.
  • Eye Gaze Tracking: Cameras or head-mounted sensors detecting where the user looks to control a cursor or robotic arm.
  • Brain-computer interfaces: EEG or implanted sensors that interpret brain activity to control external devices. These are mostly at the research and trial stage.

Specialist requirements often add complexity and cost, but they fundamentally expand accessibility and enable people with disabilities to perform tasks they could not otherwise accomplish independently.

To determine requirements, ask the people who will use the system, and their carers and therapists, what they need, and involve them in testing. Guessing what a user needs leads to devices that are unused. Then turn each need into a requirement you can test.

Developing Control Algorithms

A control algorithm reads sensors, decides what to do, and drives actuators, over and over. You develop one from the task, modify it when testing shows a problem, and apply it to the real hardware.

Developing an algorithm

  1. Define the inputs and outputs. What does the algorithm read (two reflectance sensors) and what can it command (left and right wheel speeds)?
  2. Write the rules in plain language, including the case where nothing matches.
  3. Express them in pseudocode and a flowchart using NESA notation.
  4. Trace the algorithm with test data, including boundary values, before writing any code.
  5. Code it, run it on the hardware, and record what happens.

Modifying the algorithm

Modifying the algorithm Testing shows the robot zig-zags on straight lines. Changing turnLeft() and turnRight() to slow one wheel rather than stop it gives smoother steering. Record each change and why you made it.

The zig-zag happens because the robot only has three actions, so it is always over-correcting. A better rule steers in proportion to how far the line is off centre: the further the difference between the two readings, the harder it turns.

Python — version 2: steering in proportion
BASE = 60                 # base wheel speed, percent
KP = 0.05                 # change in speed for each unit of sensor difference

def clamp(v, lo, hi):
    return max(lo, min(hi, v))

def wheel_speeds(left, right):
    correction = (right - left) * KP      # positive: the line is under the left sensor
    return clamp(BASE - correction, 0, 100), clamp(BASE + correction, 0, 100)

for left, right in [(850, 820), (300, 800), (820, 250)]:
    l, r = wheel_speeds(left, right)
    print(left, right, round(l, 1), round(r, 1))

Open and Closed Control Systems

🎯 (SE-11-02)

📌 Explore the algorithmic patterns, code and applications for open and closed control systems

The choice of control system depends on the task requirements for accuracy and self-correction. Engineers often use decision trees to map out these control paths.

Open loop and closed loop

System Type Analysis / Description Pros/Cons
Open Loop Operates on a fixed sequence or timer without feedback.A sprinkler system on a timer. Pros: Simple, low cost.
Cons: Cannot adjust to changes (e.g., if it rains).
Closed Loop Uses sensor feedback to adjust output in real-time.A thermostat maintaining room temperature. Pros: Accurate, self-correcting.
Cons: Complex, potential for instability.

More examples show the pattern. Open loop: a toaster's timer, a washing machine's fixed cycle, a stepper motor told to take 200 steps (it assumes every step happened). Closed loop: a car's cruise control (measures speed), a servo (an internal sensor reports its angle), and a drone that reads its tilt hundreds of times a second. Many systems combine both: a stepper-driven 3D printer axis moves open loop, but a limit switch closes a loop at start-up to find the home position.

The parts of a closed loop

  • Setpoint: the value you want (26 °C).
  • Sensor and feedback: the measured value that is fed back to the controller.
  • Error: setpoint minus measured value. Some systems, such as cooling, define it the other way round so a positive error opens the vent.
  • Controller: the algorithm that turns the error into a command.
  • Actuator and process: the device that acts (vent, heater) and the thing being controlled (air temperature).
  • Disturbance: anything outside the loop that pushes the process away from the setpoint, such as a cloud or an open door.

Worked example: a thermostat with a hysteresis band

The simplest closed loop is on/off control: heater on when too cold, off when warm enough. If the controller switched at exactly one temperature, the heater would flick on and off many times a minute as the reading wobbles around it, wearing out a relay. A hysteresis band (also called a dead band) fixes this with two thresholds. In the band between them, the heater keeps whatever state it already has.

pseudocode — thermostat with a hysteresis band
BEGIN thermostat
    lowLimit ← 19
    highLimit ← 21

        IF temp < lowLimit THEN
            heaterOn ← TRUE
        ELSE
            IF temp > highLimit THEN
                heaterOn ← FALSE
            ENDIF
        ENDIF
        SET heater TO heaterOn
        WAIT 1 second
    ENDWHILE
END thermostat

Features of Autonomous Control

🎯 (SE-11-02)

📌 Outline the features of an algorithm and program code used for autonomous control

Autonomous control means the system carries out its task without a person steering it. It is more than an automatic timer: an autonomous system senses its surroundings, chooses between actions and adapts when conditions change. Its program is usually organised as sense, decide, act, repeated continuously.

  • Sensor Fusion: Combining data from multiple sensors (e.g., distance sensors, IMU accelerometers, temperature sensors) to build a comprehensive understanding of the environment. Simple algorithms average sensor readings; advanced algorithms use Kalman filters for optimal estimation.
  • Decision Logic: Complex conditionals and state machines that determine what action to take based on current sensor readings and system state. Example: if an obstacle is detected within 20 cm, turn left when the left sensor is clear, otherwise turn right.
  • PID Control Loop: Proportional-Integral-Derivative control adjusts actuator output based on error (difference between desired and actual state). Common in maintaining speed, temperature, or position.
  • State Management: Tracking the current state of the system (idle, moving, gripper_open, gripper_closed) and transitioning between states safely based on sensor feedback and logic.
  • Real-Time Response: Meeting strict timing requirements, responding to sensors and issuing commands within specified time windows. Delays in real-time systems can cause crashes or safety failures.
  • Fallback Safety Logic: Default safe states (e.g., "all motors stop" if communication is lost) to prevent uncontrolled operation. A watchdog timer restarts the controller if the program stops responding.

Integrated System Design

Creating a complete mechatronic system requires simultaneous consideration of three domains:

Software Control

Algorithms and code that orchestrate sensor input, decision logic, and actuator output. Must be reliable, efficient, and responsive. In the greenhouse: read the sensors, decide with a proportional vent rule and a hysteresis pump rule, drive the servo and pump, and stop safely on a fault.

Mechanical Engineering

The physical structure, joints, materials, and mechanisms. Must support the required range of motion, handle the forces generated, and integrate smoothly with electronics. Driving a servo

A hobby servo expects a pulse every 20 ms (50 Hz). The pulse width sets the angle: many servos treat 0.5 ms as 0° and 2.5 ms as 180° (check the datasheet, as some use 1 to 2 ms). So 90° needs 500 + 90 × 2000 ÷ 180 = 1500 µs, a duty cycle of 1.5 ÷ 20 = 7.5%.

MicroPython — driving a servo with PWM
from machine import Pin, PWM

vent = PWM(Pin(15), freq=50)      # servos expect a 50 Hz signal

def set_angle(degrees):
    # 0.5 ms pulse = 0°, 2.5 ms pulse = 180°
    pulse_us = int(500 + degrees * 2000 / 180)
    vent.duty_ns(pulse_us * 1000)

set_angle(90)   # open the vent halfway

Driving a DC motor

A DC motor needs more current than a pin can give, so it is driven through an H-bridge motor driver. Two direction pins choose forward or reverse, and a PWM pin sets the speed. Keep the decision (what should the pins be?) in a pure function that can be tested on a laptop, and the hardware writes in a small separate function.

Python — turning a speed into driver pin settings
def motor_command(speed):
    """Turn a speed from -100 to 100 into (direction pin 1, direction pin 2, duty percent)."""
    speed = max(-100, min(100, speed))
    if speed > 0:
        return (1, 0, speed)
    if speed < 0:
        return (0, 1, -speed)
    return (0, 0, 0)

for s in (100, 40, 0, -60, 250):
    print(s, motor_command(s))

The last line shows why clamping matters: a command of 250 is limited to 100 before it reaches the driver.

Driving a stepper motor

A stepper turns a fixed angle for each pulse from its driver. A common motor has a 1.8° step angle, so one revolution is 360 ÷ 1.8 = 200 steps and a 90° turn is 50 steps. Microstepping splits each step: with 16 microsteps a 90° turn is 800 pulses. The program counts pulses instead of reading a sensor, which is open loop control, so an overloaded motor can silently lose steps.

Polling and interrupts

Polling checks an input each time round the main loop. It is simple, but an event that arrives during a long sleep() is noticed late. An interrupt makes the CPU pause the main program and run a short handler function as soon as the event occurs. Keep handlers very short: set a flag or switch off an output, and leave printing and slow work to the main loop. The emergency stop in the user-interface section uses this approach.

Developing a simulation

A circuit simulator such as Wokwi can run MicroPython on a virtual Raspberry Pi Pico with virtual sensors and servos. You can also write your own simulation in code. The idea is to replace the physical world with a model: a function that says how the sensor reading changes when the actuator acts. Python — testing the vent algorithm against a simulated greenhouse
def vent_angle_for(temp, setpoint=26, kp=10):
    return max(0, min(180, (temp - setpoint) * kp))

class SimGreenhouse:
    """A very simple model: the sun warms the air, an open vent cools it."""
    def __init__(self, temp=24.0, outside=20.0, sun=0.30):
        self.temp = temp
        self.outside = outside
        self.sun = sun                      # degrees gained per minute

    def step(self, vent_angle):
        cooling = 0.0005 * vent_angle * (self.temp - self.outside)
        self.temp += self.sun - cooling
        return self.temp

def run(kp, minutes=60):
    room = SimGreenhouse()
    angle = 0
    for _ in range(minutes):
        temp = room.step(angle)
        angle = vent_angle_for(temp, kp=kp)
    return round(room.temp, 1), round(angle)

for kp in (10, 30, 60):

Programming a Closed Loop Control System

🎯 (SE-11-02, SE-11-07)

📌 Design, develop and implement programming code for a closed loop control system

Closed loop systems use sensor feedback to adjust actuator output continuously. Implementation requires:

  • Clearly defining the setpoint (desired state) and feedback (actual state).
  • Calculating the error (setpoint − feedback, or feedback − setpoint if the system cools).
  • Applying a control algorithm (on/off with hysteresis, proportional, PID, fuzzy logic, state machine) to generate corrective output.
  • Iterating: reading sensors, calculating, and updating actuators in a tight loop. The right rate depends on how fast the system changes: a greenhouse might loop once a second, a self-balancing robot hundreds of times a second.

Proportional control

MicroPython — closed loop vent control
SETPOINT = 26          # °C we want to hold
KP = 10                # degrees of vent per °C of error

while True:
    temp = read_temperature()          # feedback: the actual state
    error = temp - SETPOINT            # this loop cools, so hotter than the setpoint = positive error
    angle = max(0, min(180, error * KP))  # bigger error → wider vent, limited to the servo's range
    set_angle(angle)                   # act on the error
    sleep(1)                           # repeat once a second

Adding an integral term: PID

The simulation earlier showed proportional control settling above the setpoint: when the error is small, so is the correction, so a small error can persist. This is steady-state error. An integral term adds up the error over time, so a persistent error keeps growing the correction until the error is gone. A derivative term reacts to how fast the error is changing, which damps overshoot. Together with the proportional term they make a PID controller. Add the code below to the simulation from the previous part (it reuses SimGreenhouse):

Python — proportional and integral control (PI)
class PID:
    def __init__(self, kp, ki=0.0, low=0, high=180):
        self.kp, self.ki = kp, ki
        self.low, self.high = low, high
        self.integral = 0.0

    def update(self, error, dt=1):
        """Return the vent angle for this error (measured minus setpoint)."""
        command = self.kp * error + self.ki * self.integral
        if self.low < command < self.high:      # anti-windup: stop adding up while the vent is at its limit
            self.integral += error * dt
        return max(self.low, min(self.high, command))

def run_pid(controller, minutes=240):
    room = SimGreenhouse()
    angle = 0
    for _ in range(minutes):
        temp = room.step(angle)
        angle = controller.update(temp - 26)
    return round(room.temp, 1), round(angle)

print("P only :", run_pid(PID(kp=30)))
print("P and I:", run_pid(PID(kp=30, ki=1.0)))
Expected output (temperature and vent angle after 240 minutes)

The integral term removed the 2.4 °C offset. Anti-windup matters: if the vent is fully open and the room is still too warm, an unchecked integral would keep growing and the controller would overshoot for a long time after conditions change.

Python — control.py (decision logic, no hardware)
# control.py - the decision logic only. It imports no hardware modules,
# so it can be tested on a laptop with ordinary Python.
SETPOINT = 26                      # °C to hold
KP = 10                            # degrees of vent per °C of error
DRY_RAW, WET_RAW = 45000, 20000    # calibration: readings in dry air and in water
PUMP_ON_BELOW = 30                 # % moisture
PUMP_OFF_ABOVE = 45

def raw_to_celsius(raw, vref=3.3):
    volts = raw / 65535 * vref
    return (volts - 0.5) * 100     # TMP36: 10 mV per °C, 0.5 V at 0 °C

def raw_to_moisture(raw):
    percent = (DRY_RAW - raw) * 100 / (DRY_RAW - WET_RAW)
    return max(0, min(100, percent))

def sensor_ok(temp):
    return -10 < temp < 60         # anything outside this range means a fault

def vent_angle_for(temp, setpoint=SETPOINT, kp=KP):
    return max(0, min(180, (temp - setpoint) * kp))

def pump_next_state(pump_on, moisture):
    if moisture < PUMP_ON_BELOW:
        return True
    if moisture > PUMP_OFF_ABOVE:
        return False
    return pump_on                 # inside the band: keep the current state

def smooth(readings, new, size=5):
    readings.append(new)
    if len(readings) > size:
        readings.pop(0)            # keep only the last 5 readings
    return sum(readings) / len(readings)

# (1) Hardware, matching the wiring table

stopped = False
pump_locked = False
pump_started = 0

    vent.duty_ns(int(500 + degrees * 2000 / 180) * 1000)

    global stopped
    pump.off()
    stopped = True

    moisture = control.raw_to_moisture(soil_adc.read_u16())

    if not control.sensor_ok(raw_temp):        # (7) fail safe
        pump.off()
        print("SENSOR FAULT: pump off")
    else:
        temp = control.smooth(readings, raw_temp)                  # (8) decide and act: vent
        angle = control.vent_angle_for(temp)
        set_angle(angle)

        wanted = control.pump_next_state(pump.value() == 1, moisture)   # (9) decide and act: pump
        if wanted and not pump_locked:
            if not pump.value():
                pump_started = utime.ticks_ms()
            pump.on()
            if utime.ticks_diff(utime.ticks_ms(), pump_started) > PUMP_MAX_MS:
                pump.off()
                pump_locked = True             # needs a restart: something is wrong
                print("PUMP TIMEOUT")
        else:
            pump.off()

        print("temp %.1f C  vent %d deg  soil %d%%  pump %s" %      # (10) log
              (temp, round(angle), round(moisture), "ON" if pump.value() else "OFF"))
    utime.sleep(1)

vent.duty_ns(0)                                # (11) stop driving the servo
print("STOPPED")

Control Algorithms That Enhance Performance

🎯 (SE-11-08)

📌 Implement specific control algorithms that enhance the performance of a mechatronic system

Control Algorithm Optimisation

Performance means how quickly, accurately, smoothly and reliably the system does its job. Specific algorithms enhance it:

TechniqueProblem it solvesCost or risk
PID tuningSlow response, overshoot, steady-state errorNeeds testing; wrong gains oscillate
Acceleration rampingJerky starts, wheel slip, current surgesSlower to reach full speed

  • PID Tuning: Adjusting proportional, integral, and derivative gains to achieve fast, stable response without overshoot. A practical method: start with Ki and Kd at zero; raise Kp until the system responds quickly; if it oscillates, back Kp off; then add a little Ki to remove the steady-state error, and Kd only if overshoot remains.   • Acceleration Ramping: Gradually increasing motor speed to reduce jerky movements and mechanical stress.
  • Sensor Filtering: Averaging or smoothing noisy sensor readings to improve decision quality.

Sensor filtering

MicroPython — smoothing a noisy sensor
readings = []

def smoothed_temperature():
    readings.append(read_temperature())
    if len(readings) > 5:
        readings.pop(0)                 # keep the last 5 readings
    return sum(readings) / len(readings)  # moving average

Without smoothing, a single noisy reading can make the vent twitch open and shut. Averaging the last five readings makes the system calmer, and the servo lasts longer. Different filters suit different noise, so compare them on the same data:

Python — three filters on a reading with a spike
def moving_average(values):
    return sum(values) / len(values)

def median(values):
    ordered = sorted(values)
    return ordered[len(ordered) // 2]

def exponential(previous, new, alpha=0.3):
    return alpha * new + (1 - alpha) * previous

readings = [24.0, 24.2, 30.9, 24.1, 24.3]        # 30.9 is a one-off spike

print("Average:", round(moving_average(readings), 1))
print("Median :", median(readings))

smoothed = readings[0]
for value in readings[1:]:
    smoothed = exponential(smoothed, value)
print("Exponential:", round(smoothed, 1))
Expected output
Average: 25.5
Median : 24.2
Exponential: 25.1

The true temperature is about 24.2 °C. The average and the exponential filter are both pulled up by the spike; the median ignores it. The average is the simplest choice for random noise; the median is better for occasional spikes; the exponential filter needs no list of past readings, so it uses little memory. Every filter adds lag, so a heavily filtered sensor reacts late to real change.

Acceleration ramping

Jumping a motor from 0 to full speed draws a large current surge, can make wheels slip and jolts a payload. A ramp limits how much the command can change each loop:

Python — limiting the change in speed
def ramp(current, target, max_step=10):
    if target > current:
        return min(target, current + max_step)
    return max(target, current - max_step)

speed = 0
for _ in range(6):
    speed = ramp(speed, 45)
    print(speed, end=" ")
print()

Timing without blocking

Calling sleep(1) stops the whole program for a second, so a button press or a second sensor cannot be checked. Instead, record when the last control step ran and act only when enough time has passed:

MicroPython — a control step once a second without blocking
import utime

last_step = utime.ticks_ms()

while True:
    now = utime.ticks_ms()
    if utime.ticks_diff(now, last_step) >= 1000:   # one second has passed
        last_step = now
        control_step()                             # read, decide, act
    check_buttons()                                # runs on every pass, many times a second

Unit Testing Control Algorithms

Mechatronic systems require rigorous testing of each component. A unit test checks one small piece (a function or a single device) against a known input and an expected result. Tests protect against mistakes made later. If someone removed the max(0, …) from vent_angle_for, the vent would be commanded to a negative angle when the room is cool, and test_closed_when_cool would fail straight away. A test that fails for the right reason is a success: it found the bug before the greenhouse did. (MicroPython has no built-in test framework, which is another reason to keep logic in a file that also runs on a laptop.)

Testing and calibrating sensors

Real sensors are not perfect: two identical parts can read differently, and readings drift with temperature and age. Calibration compares the sensor with a known reference and corrects the difference. A two-point calibration uses a low and a high reference and draws a straight line between them.

  1. Measure the sensor in a low reference (ice water, close to 0 °C) and a high reference (boiling water, close to 100 °C at sea level; use a reference thermometer if you have one). Say the sensor reads 1.8 °C and 97.5 °C.
  2. Work out the gain: (100 − 0) ÷ (97.5 − 1.8) ≈ 1.045.
  3. Correct every later reading: corrected = 0 + (reading − 1.8) × 1.045.
  4. Check the result against a third reference, such as a room-temperature thermometer.
Python — two-point calibration
def make_calibration(raw_low, ref_low, raw_high, ref_high):
    gain = (ref_high - ref_low) / (raw_high - raw_low)
    return lambda raw: ref_low + (raw - raw_low) * gain

correct = make_calibration(1.8, 0.0, 97.5, 100.0)
print(round(correct(1.8), 1), round(correct(97.5), 1), round(correct(25.0), 1))
Expected output
0.0 100.0 24.2

The soil moisture sensor is calibrated the same way: record its raw reading in dry air (DRY_RAW) and in a glass of water, up to its marked line (WET_RAW), and the program maps the range between them to 0–100%. Record every calibration with the date, the references used and the values found, and repeat it when a sensor is replaced.

Repeatability

Repeatability testing ensures the system behaves consistently across multiple trials—critical for autonomous systems where unpredictable behaviour is unacceptable. Logging sensor data and actuator commands during tests helps engineers debug failures and improve reliability. Set a pass criterion before testing, then compare.

Python — judging repeatability from five trials
trials = [30, 29, 31, 30, 30]          # vent angle (degrees) after heating the sensor to 29 C, five runs
target, tolerance = 30, 3
mean = sum(trials) / len(trials)
spread = max(trials) - min(trials)
print("mean", mean, "spread", spread, "PASS" if abs(mean - target) <= tolerance and spread <= 2 * tolerance else "FAIL")
Expected output
mean 30.0 spread 2 PASS

Because the algorithm is a separate function, it can be tested on a laptop without any hardware. Repeatability is then checked on the real system by running the same test several times, for example heating the sensor to 29 °C five times and confirming the vent reaches about 30° each time. The trial values above are example data; on a real system you record your own. A small spread means the system is repeatable; a large spread points to a loose linkage, a noisy sensor or unstable code.
