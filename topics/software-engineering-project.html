Why this matters now

Real software is never built by writing code alone. Tech companies ship through cycles of requirements, design, prototyping, testing and feedback, and the difference between a successful launch and an expensive failure is usually planning, not programming talent. Your major project is your chance to work the way professional engineers do, and a well-documented portfolio is something you can show future universities and employers.

In this topic you will work through the syllabus content on defining requirements, generating and communicating ideas, choosing a development approach such as Waterfall or Agile, managing your project, and testing and evaluating your solution.

Start with this question What real problem, for a real person, could your project solve?

See a complete example The Example Major Project follows every step on this page, from brief and requirements to tests and evaluation, for a smart greenhouse controller you can run in your browser.

Defining and Analysing Requirements

Problem Requirements

Before coding begins, a software engineer must define the core requirements:

  • 🎯 Demonstrating needs or opportunities: Clearly identifying the real-world problem the software solves for the client.
  • 💰 Assessing scheduling and financial feasibility: Determining if the project can be completed within the allocated timeframe and budget.
  • 📝 Generating requirements: Defining functionality (what the system must do) and performance (how well/fast it must do it).
  • 🗄️ Defining data structures and types: Specifying how information will be securely collected and stored.
  • 🚧 Defining boundaries: Establishing the scope to prevent "scope creep" during development.

Demonstrating a need or an opportunity

A need is a problem that real people have now. An opportunity is a chance to do something better that nobody has complained about yet. Either way you must demonstrate it with evidence from the people affected, not assume it. Useful evidence is an interview, an observation of the current process, samples of the current records, a short survey, or a measurement (such as how long a task takes today).

TermWhat it isLibrary Loans example
NeedThe problem to be solved, in the client's words"I type the overdue list by hand every Friday, and I can't tell from the desk whether a book is in."
RequirementA testable statement of what the solution must do (functional) or how well (non-functional)"Staff can view a list of every overdue loan with the member, title and days overdue."
ConstraintA limit on how the project may be done: time, money, skills, technology, law, policy"Seven weeks, one developer, free tools only, no student data leaves the school network."
BoundaryThe line around what the system will and will not do"Loans, returns, search and overdue lists are inside. Email reminders and fine payment are outside."
Worked example: a need statement
  • Who: Mrs Chen (client), library volunteers, and students who borrow books.
  • Problem: loans are stamped on paper cards, so checking whether a book is in means walking to the shelf or searching the cards. The overdue list is typed by hand each Friday, and some due dates on old cards cannot be read.
  • Evidence: an interview with Mrs Chen (notes filed in the process diary), an observation of one lunchtime at the desk, and three photographed cards with unreadable dates.
  • Need: record a loan or a return in seconds and produce the overdue list automatically.
  • Opportunity: once loans are stored as data, the library could later see which titles are borrowed most. Nobody has asked for this yet, so it is an opportunity and not a requirement.

Assessing scheduling and financial feasibility

Feasibility asks whether the project can realistically be finished with the time and money available. Estimate the effort task by task, add a contingency for things that go wrong (10% to 20% is common), and compare the total with the time you actually have. Do this before promising features to the client.

  • Core scope with 15% contingency: 42 × 1.15 = 48.3 hours. This is less than 49 hours, so the core scope is schedule-feasible, with only 0.7 hours to spare.
  • Core scope plus email reminders: (42 + 8) × 1.15 = 57.5 hours. This is more than 49 hours, so it is not feasible.
  • Financial feasibility: the project uses only free tools (VS Code, Python, SQLite, Git and GitHub) and the library's existing computer, so the cash cost is $0. A costed budget for a paying client is worked through in Applying Project Management.
  • Decision: email reminders are put outside the boundary for version 1 and recorded as a possible later version. Mrs Chen agrees, because the overdue list she needs most is still delivered.

User Stories and Acceptance Criteria

User stories capture requirements from the end-user's perspective in plain language. They follow the format: "As a [role], I want [feature], so that [benefit]." Each user story is accompanied by acceptance criteria — specific, testable conditions that confirm the story has been implemented correctly.

User Story Acceptance Criteria
As a library member, I want to search for books by title so that I can quickly check if a book is available.
  • Search returns results within 2 seconds
  • Results display title, author, and availability status
  • Partial title matches are returned (e.g., "Harry" returns all Harry Potter books)
  • A "no results found" message displays for unmatched queries
As a staff member, I want to issue a loan so that the member can borrow the book and a return date is recorded.
  • System prevents issuing a loan if member already has 5 active loans
  • Due date is automatically set to 14 days from issue date
  • Book availability status changes to "On Loan" immediately
  • A confirmation message is displayed on success
As an administrator, I want to generate an overdue report so that I can contact members with outstanding returns.
  • Report lists all loans where current date exceeds the due date
  • Report can be filtered by member name or overdue duration
  • Report can be exported as a CSV file

Defining data structures and data types

Requirements say what information the system handles. You then decide how each item is typed (text, whole number, decimal, date, true/false) and how items are structured (a single variable, a list, a dictionary of records, a database table). Choose the simplest type that stores the value correctly and lets you validate it.

from datetime import date

Constraints and boundaries

A constraint limits how the project may be carried out. A boundary defines what the system will and will not do. Together they protect the project from scope creep, the slow growth of requirements that nobody has costed.

Kind of constraintLibrary Loans example
TimeSeven weeks, with a 15-minute client review every second Friday.
MoneyNo budget: free tools only.
SkillsOne developer who knows Python, SQLite and Flask, but not mobile apps.
TechnologyMust run on the library's existing computer, with no internet needed at the desk.
Law and policyStudent names and IDs are personal information, so the school's privacy obligations apply. Data stays on the school network.

The system boundary is shown on the Level 0 data flow diagram in Using Modelling Tools: students, the librarian and the school admin system are outside the boundary, and the Library Loans system is inside. A written scope statement makes the same boundary explicit.

Inside the boundary (version 1)Outside the boundary
Search the catalogue, issue and return loans, view the overdue list, calculate fines, export CSV, staff sign-inEmail or SMS reminders, online payment of fines, a student login, a mobile app, ordering new books

Handling a change request. When Mrs Chen asks for something outside the boundary: (1) write the request down; (2) estimate its hours; (3) show the effect on the schedule (the email reminders in the feasibility example added 8 hours and made the project infeasible); (4) let the client decide to swap it for something else, extend the deadline or defer it; (5) record the decision in the process diary. Boundaries also exist inside the data. "A member may hold at most 5 loans" is a boundary that later becomes boundary test data at 4, 5 and 6.

A strong requirements section includes
  • A clear problem statement backed by evidence that a real person has the problem, not just "I made an app because it is interesting".
  • Both requirement types. Documenting only functional requirements is a common gap, and non-functional requirements (performance, security, usability, maintainability) are what you evaluate against later.
  • Evidence of client involvement: meeting notes, interview notes or a survey summary.
  • Feasibility worked out with numbers for time and money, and the decision it led to.
  • Measurable wording (Specific, Measurable, Achievable, Realistic, Time-bound). Avoid "the system should be fast". Write "search returns within 2 seconds".

Your school's assessment notification says which of these it marks. Use it alongside this checklist.

Exam tip: "Define" and "analyse" requirements Expect scenario questions such as "Identify one functional and one non-functional requirement for the system described" or "Outline two constraints the developer must consider". A full-mark answer names the item and ties it to the scenario: "Non-functional: search must return within 2 seconds for 10,000 titles (performance), because staff use it at a busy lunchtime desk." Common mistakes are writing a feature ("has a search bar") as a non-functional requirement, giving a requirement that cannot be tested ("user friendly"), and confusing a constraint (a limit on the project, such as the deadline) with a boundary (a limit on the system's scope).

Brainstorming and mind-mapping

Brainstorming is a short burst of ideas with no judging, so quantity comes before quality. Mind-mapping then organises the ideas around a central topic, with branches for groups and sub-branches for detail. The two steps work as a pair: diverge (collect everything), then converge (sort, cut and choose using the requirements and constraints).

Worked example. In five minutes the student and Mrs Chen list everything the library system could do: scan barcodes, email reminders, search by title, fines, staff sign-in, student photos, reserve a study room, print the overdue list, reading recommendations, renew a loan. The mind map below groups those ideas, and the constraints from the previous section decide which branches are built now.

  • Library Loans
    • Loans (build now): issue, return, loan limit; renew (later)
    • Catalogue (build now): search by title or ISBN, availability
    • Reports (build now): overdue list, fines, CSV export
    • Members (build now): name and ID only; staff sign-in
    • Later versions: email reminders, reserving a study room, recommendations
    • Rejected: student photos (privacy risk and no client need)

Storyboards and Wireframes

A storyboard visually maps the sequence of screens a user encounters when completing a task. A wireframe is a low-fidelity layout sketch of a single screen, showing the placement of UI elements without colour or detailed styling. Together, they allow client feedback on the interface before any front-end code is written.

Storyboard vs Wireframe — Key Differences
  • Storyboard: Shows a sequence of interactions — e.g., the steps a user takes from the login screen to completing a book search. Think of it as a comic strip of your application's workflow.
  • Wireframe: Shows the layout of a single screen — where headers, navigation, input fields, and buttons are positioned. It does not include colour, fonts, or images.
  • Prototype: A clickable, interactive mock-up of the interface, often built in a tool like Figma or Canva. It simulates real user interaction without any back-end code.
  • Why include them: They show that you consulted the client about the UI before coding, which is a hallmark of professional software engineering practice.

A data dictionary formally defines every data item used in the system — its name, data type, size, valid range, and description. It ensures consistency between the design documents and the code implementation, and establishes the data structures required for the project.

Algorithm design

An algorithm is the step-by-step logic of a solution, written before the code. NESA's Course Specifications ask for algorithms as pseudocode or flowcharts, built from sequence, selection and repetition. In pseudocode keywords are capitals, structures come in pairs (every IF has an ENDIF, every BEGIN has an END), indentation shows the structure, and a subroutine is called by name with its own algorithm written separately. Start with a short mainline that calls subroutines.

pseudocode: mainline
BEGIN LibraryLoans
    SignIn
    REPEAT
        DisplayMenu
        Get choice
        CASEWHERE choice evaluates to
            1: IssueLoan
            2: ReturnBook
            3: SearchCatalogue
            4: OverdueReport
            5: Display "Goodbye"
            OTHERWISE: Display "Choose a number from 1 to 5"
        END CASE
    UNTIL choice = 5
END LibraryLoans

One subroutine in detail: the fine for a loan (requirement FR6, 20 cents a day up to $10.00). The fine is held in cents so the arithmetic is exact. This is a nested IF, with one ENDIF for each IF.

pseudocode: subroutine with a nested IF
BEGIN CalculateFine (daysOverdue, fine)
    IF daysOverdue <= 0 THEN
        fine = 0
    ELSE
        IF daysOverdue > 50 THEN
            fine = 1000
        ELSE
            fine = daysOverdue * 20
        ENDIF
    ENDIF
END CalculateFine (daysOverdue, fine)

Python: the same algorithm
def calculate_fine_cents(days_overdue):
    """Return the fine in cents: 20 cents a day, capped at 1000 (ten dollars)."""
    if days_overdue <= 0:
        fine = 0
    else:
        if days_overdue > 50:
            fine = 1000
        else:
            fine = days_overdue * 20
    return fine


for days in (0, 1, 50, 51):
    print(days, calculate_fine_cents(days))

Expected output: 0 0, 1 20, 50 1000, 51 1000, matching the trace table.

Code generation

Code generation is turning a design into working code. It can be done by hand, guided by the design documents, or with tools that produce code from a description: templates and project scaffolds, IDE features that create class or function outlines, tools that create database code from a schema, and generative AI assistants. Whatever produces the first draft, you remain responsible for understanding, testing and acknowledging it.

Testing and debugging

Testing finds out whether the software fails; debugging finds out why and fixes it. Both are tools for developing solutions, not only a stage at the end: test each module as you write it. Common debugging tools are print statements or a logger, an IDE breakpoint with single-step execution, and a trace table on paper. Part 4 covers the full methodology.

Worked example (defect BUG-002). The loan limit test fails: a member with 5 loans is allowed a sixth. Reproduce it, isolate the condition, then fix it.

Python: reproduce, then fix
def can_borrow(active_loans, limit=5):
    return active_loans <= limit      # bug: 5 <= 5 is True, so a sixth loan is allowed


print(can_borrow(5))                    # expected False, actual True

# Fix: a member may borrow only while they hold FEWER than the limit
def can_borrow(active_loans, limit=5):
    return active_loans < limit


print(can_borrow(5))                    # False
print(can_borrow(4))                    # True

Expected output: True, then False, then True. The first line shows the defect. The last two show the boundary now behaves correctly.

The Waterfall Approach

🎯 (SE-12-01, SE-12-09)

📌 Research and use the Waterfall software development approach

  • logical progression of steps used throughout the life cycle
  • stages of ‘falling water’
  • advantages and disadvantages
  • scale and types of developments

Waterfall works through the development steps one at a time, in order. Each stage is finished and signed off before the next begins, so the project flows downwards like water over a series of ledges.

  • Logical progression of steps: requirements → design → development → testing → installation → maintenance. Each stage produces documents that the next stage relies on.
  • Stages of 'falling water': going back up is difficult and expensive. A change found during testing may mean redoing design and development.

Clear milestones and deadlines that are easy to trackHard to respond when the client changes their mind
Thorough documentation at every stageThe client sees working software only near the end
Easy to estimate cost and time up frontProblems are often found late, when they cost the most to fix

Scale and types of developments: Waterfall suits large projects with stable, well-understood requirements and strict regulation, such as a hospital records system or an aircraft control system.

The Agile Approach

🎯 (SE-12-01, SE-12-09)

📌 Research and use the Agile software development approach

  • rate of developing a final solution
  • method tailoring
  • iteration workflow
  • scale and types of developments

Agile builds software in short cycles called iterations or sprints. Each cycle delivers a small working piece that the client can try and give feedback on, so the plan keeps adjusting as the project goes.

  • Rate of developing a final solution: a usable version appears early and improves every sprint, so value arrives sooner than in Waterfall.
  • Method tailoring: teams adapt the process to suit the project, for example choosing one-week sprints or skipping formal ceremonies in a small team.
  • Iteration workflow: plan → build → test → review with the client → adjust, then repeat.
  • Scale and types of developments: best for small to medium projects where requirements are likely to change, such as a start-up's mobile app or a school's online booking system.

The WAgile Approach

🎯 (SE-12-01, SE-12-09)

📌 Research the WAgile software development approach

  • understanding it is a hybrid model
  • analysis of the ‘when’ and ‘how’ intervention is applied during the development life cycle

WAgile is a hybrid model: it plans and closes a project the Waterfall way but builds the software in Agile sprints.

  • When intervention is applied: at fixed checkpoints, such as signing off requirements, approving a design, and a final security audit before release.
  • How intervention is applied: through formal reviews and sign-offs at those gates. Between them, the team works in sprints and adapts to feedback.
  • Scale and types of developments: medium to large projects that need both flexibility and firm control, such as a bank adding a new feature to an existing regulated system.

Gantt Chart — Project Schedule

A Gantt chart is a horizontal bar chart that maps project tasks against a timeline. It visually shows the start date, duration, and end date of each task, and can indicate task dependencies (where one task must complete before another begins). A useful Gantt chart for your project covers all four syllabus phases (identify and define, research and plan, produce and implement, test and evaluate), so it is easy to show that no phase was skipped.

What a Gantt chart must show

NESA's Course Specifications (p. 11) say a Gantt chart displays each component task on an estimated timeline, and list what it should show:

  • Self-explanatory task names ("Search module", not "Task 4").
  • The estimated time for each task and its dependent tasks, meaning tasks that cannot start until another finishes.
  • A time scale with dates, and important milestones clearly marked.
  • Optionally, resources: the chart can allocate team members to tasks and show each person's percentage completion.
  • Regular updates during development to compare actual with estimated times.

Worked example: dependencies, float and the critical path

Some tasks can run at the same time; others must wait. The critical path is the longest chain of dependent tasks, and it decides the earliest finish date. (The critical path is a standard planning technique; NESA's specification asks for dependencies and milestones and does not name it, but it is the way to find which dependencies matter most.) For each task, work out four times and one number:

  • ES (earliest start) is the latest EF of the tasks it depends on, or 0 if there are none. EF (earliest finish) = ES + duration. This is the forward pass.
  • LF (latest finish) is the earliest LS of the tasks that depend on it, or the project end if none do. LS (latest start) = LF − duration. This is the backward pass.
  • Float (slack) = LS − ES. It is how many days a task can slip without delaying the project. Tasks with zero float are critical.

To reproduce the table in code, the passes are short. This program computes the same numbers.

Python: forward and backward pass
tasks = {
    "A": (5, []),
    "B": (3, ["A"]),
    "C": (4, ["B"]),
    "D": (5, ["B"]),
    "E": (8, ["C"]),
    "F": (6, ["C"]),
    "G": (7, ["D", "F"]),
    "H": (4, ["E", "G"]),
    "I": (6, ["C"]),
    "J": (3, ["H", "I"]),
}

early = {}
for name, (days, before) in tasks.items():          # forward pass
    start = max((early[p][1] for p in before), default=0)
    early[name] = (start, start + days)

project = max(finish for start, finish in early.values())

late = {}
for name in reversed(list(tasks)):                   # backward pass
    days = tasks[name][0]
    after = [n for n, (d, before) in tasks.items() if name in before]
    finish = min((late[n][0] for n in after), default=project)
    late[name] = (finish - days, finish)

print(f"Project duration: {project} days")
for name in tasks:
    spare = late[name][0] - early[name][0]
    print(name, "early", early[name], "late", late[name], "float", spare, "CRITICAL" if spare == 0 else "")

Expected output: Project duration: 32 days, then one line per task. Tasks A, B, C, F, G, H and J print CRITICAL; D and E print float 5 and I prints float 11. For example, the line for D is D early (8, 13) late (13, 18) float 5.

The Contribution of Back-End Engineering

🎯 (SE-12-02, SE-12-03)

📌 Explain the contribution of back-end engineering to the success and ease of software development

  • technology used
  • error handling
  • interfacing with front end
  • security engineering

Explain the contribution of back-end engineering to the success and ease of software development:

Technology Used

The selection of server-side frameworks and database technologies fundamentally determines a project's performance, scalability, and long-term maintainability. For example, a Django (Python) framework provides a built-in ORM, authentication system, and admin panel — reducing development time for data-driven applications. Alternatively, Node.js enables non-blocking I/O suited to high-concurrency environments, such as real-time chat applications. Database choice is equally critical: a relational database such as PostgreSQL enforces data integrity through foreign keys and ACID transactions, whereas a NoSQL database such as MongoDB offers flexible document schemas suited to rapidly evolving data models.

Error Handling

Robust error handling ensures the server remains stable and informative when unexpected inputs or system failures occur. Without it, an unhandled exception could crash the entire server process — making the application unavailable to all users simultaneously. For example, a try/except block in Python can catch a database connection timeout and return a user-friendly 503 Service Unavailable HTTP response, rather than exposing a raw stack trace to the client. Also, structured logging (e.g., Python's logging module) records error details for post-mortem debugging, without leaking sensitive system information to end-users.

Interfacing with Front End

Back-end engineers design Application Programming Interfaces (APIs) that define precisely how the front-end client requests and receives data. A RESTful API uses standard HTTP methods (GET, POST, PUT, DELETE) with JSON payloads, allowing any front-end technology — React, Angular, or a mobile app — to consume the same endpoints without modification. For example, a GET request to /api/students/42 would return a JSON object containing that student's profile. Efficient API design minimises data transfer by returning only required fields, and uses HTTP status codes correctly (200 OK, 404 Not Found, 401 Unauthorised) so the front end can respond appropriately to every outcome.

Security Engineering

The back end is the primary line of defence against malicious attacks. Password security is implemented through cryptographic hashing algorithms such as bcrypt, which store a one-way hash rather than plaintext — meaning a complete database breach still cannot reveal user credentials. Input sanitisation and parameterised SQL queries prevent SQL injection attacks, where an attacker might otherwise embed SQL commands in a form field to manipulate or delete database records. Also, implementing HTTPS with TLS certificates encrypts all data in transit, protecting against man-in-the-middle attacks on public networks.

    """Return one member as JSON, or a clear error the front end can act on."""
    try:
        with sqlite3.connect(DB_PATH) as db:

                "SELECT member_id, name FROM members WHERE member_id = ?",   # (4) security: parameterised query

Passwords need the same care. The next program stores a random salt with a slow hash, so identical passwords give different stored values and a stolen database does not reveal them (libraries such as bcrypt do this for you and are the usual choice in a real project; this version uses only Python's standard library).

Python: salted, slow password hash
import hashlib
import hmac
import os


def hash_password(password):
    """Return salt + slow hash. The salt is random, so equal passwords give different results."""
    salt = os.urandom(16)
    digest = hashlib.pbkdf2_hmac("sha256", password.encode(), salt, 200_000)
    return salt + digest


def check_password(password, stored):
    salt, digest = stored[:16], stored[16:]
    attempt = hashlib.pbkdf2_hmac("sha256", password.encode(), salt, 200_000)
    return hmac.compare_digest(attempt, digest)


stored = hash_password("correct horse battery")
print(check_password("correct horse battery", stored))
print(check_password("Password1", stored))
print(hash_password("same") == hash_password("same"))

  • Trust. Security built in at the back end protects the client and the people whose data is stored, and avoids expensive retrofits later.
  • Speed of development. A well-chosen framework and database supply common features (routing, sessions, migrations), so effort goes into the client's actual problem.

Modular Design — Python Example

A well-engineered solution separates concerns into distinct modules and classes. The example below shows how the Library Management System is implemented using modular Python, with each class responsible for a single aspect of the system.

Python — Modular Design: Library System
"""
Library Management System — Modular Python Design
Demonstrates separation of concerns across classes.
"""

# ── DATA LAYER ─────────────────────────────────────────────
class Book:
    """Represents a single book in the library catalogue."""
    def __init__(self, isbn: str, title: str, author: str):
        self.isbn = isbn
        self.title = title
        self.author = author
        self.available = True

    def __repr__(self):
        status = "Available" if self.available else "On Loan"
        return f"Book({self.title!r} by {self.author} — {status})"


class Member:
    """Represents a library member."""
    MAX_LOANS = 5

    def __init__(self, member_id: str, name: str, email: str):
        self.member_id = member_id
        self.name = name
        self.email = email
        self.active_loans = []

    def can_borrow(self) -> bool:
        return len(self.active_loans) < self.MAX_LOANS


# ── SERVICE LAYER ──────────────────────────────────────────
class LoanService:
    """Handles all business logic for issuing and returning loans."""

    def __init__(self):
        self.loans = []  # In a real system, this would query a database

    def issue_loan(self, book: Book, member: Member) -> str:
        """Issue a loan if the book is available and member can borrow."""
        if not book.available:
            return f"Error: '{book.title}' is currently on loan."
        if not member.can_borrow():
            return f"Error: {member.name} has reached the maximum loan limit."

        book.available = False
        member.active_loans.append(book.isbn)
        self.loans.append({"isbn": book.isbn, "member_id": member.member_id})
        return f"Success: '{book.title}' issued to {member.name}."

    def return_book(self, book: Book, member: Member) -> str:
        """Process a book return."""
        if book.isbn not in member.active_loans:
            return f"Error: No active loan found for '{book.title}'."
        book.available = True
        member.active_loans.remove(book.isbn)
        return f"Success: '{book.title}' returned by {member.name}."


# ── SEARCH MODULE ──────────────────────────────────────────
class Catalogue:
    """Manages the book catalogue and provides search functionality."""

    def __init__(self):
        self.books: list[Book] = []

    def add_book(self, book: Book):
        self.books.append(book)

    def search_by_title(self, query: str) -> list[Book]:
        """Case-insensitive partial title search."""
        query = query.lower()
        return [b for b in self.books if query in b.title.lower()]

    def search_by_isbn(self, isbn: str) -> Book | None:
        """Return the book matching the given ISBN, or None."""
        return next((b for b in self.books if b.isbn == isbn), None)


# ── MAIN PROGRAM ───────────────────────────────────────────
if __name__ == "__main__":
    catalogue = Catalogue()
    loan_service = LoanService()

    book1 = Book("978-0-7432-7356-5", "The Great Gatsby", "F. Scott Fitzgerald")

    print(catalogue.search_by_title("gatsby"))
    print(loan_service.issue_loan(book1, member1))

Developing and Documenting Algorithms

🎯 (SE-12-02, SE-12-09)

📌 Develop, construct and document algorithms

Before and during coding, write the key parts of your solution as algorithms, then keep them with your documentation so others can follow your logic.

  • Develop: plan the logic in pseudocode or a flowchart before you write code.
  • Construct: turn each algorithm into code, one subroutine at a time.
  • Document: keep the final algorithms, with comments and a short description of inputs, outputs and purpose.

NESA's Course Specifications expect algorithms as pseudocode or flowcharts using the standard control structures. The March 2026 specifications show a nested IF as an ELSE that holds another IF, with one ENDIF for every IF. Write it that way.

Develop: plan the logic

Start with the decision rules. FR2 and FR3 say a loan needs an available book and a member under the limit. That is the decision tree from Part 2, now as an algorithm that returns a single value, so it is written as a function.

pseudocode: a function with a nested IF
BEGIN CanIssueLoan (bookAvailable, activeLoans, allowed)
    IF bookAvailable = False THEN
        allowed = False
    ELSE
        IF activeLoans >= 5 THEN
            allowed = False
        ELSE
            allowed = True
        ENDIF
    ENDIF
END CanIssueLoan (bookAvailable, activeLoans, allowed)

Construct: turn it into code

Each algorithm becomes one function with the same name and the same decisions, so a reader can lay the pseudocode beside the code. A second algorithm, for a feature proposed for a later version (reserving a study room), uses a repetition and a condition with AND. Times are in minutes after midnight, and a new booking clashes if it starts before an existing one finishes and finishes after it starts.

pseudocode: repetition with a condition
BEGIN CheckClash (newRoom, newStart, newFinish, clash)
    clash = False
    FOR i = 1 TO bookingCount
        IF bookedRoom[i] = newRoom AND newStart < bookedFinish[i] AND newFinish > bookedStart[i] THEN
            clash = True
        ENDIF
    NEXT i
END CheckClash (newRoom, newStart, newFinish, clash)
Python: the same algorithm
def has_clash(new_room, new_start, new_finish, bookings):
    """Return True if the new booking overlaps an existing one in the same room.
    Times are minutes after midnight."""
    clash = False
    for room, start, finish in bookings:
        if room == new_room and new_start < finish and new_finish > start:
            clash = True
    return clash


bookings = [(2, 600, 660)]                 # room 2, 10:00 to 11:00
print(has_clash(2, 630, 690, bookings))    # 10:30 to 11:30  -> overlaps
print(has_clash(2, 660, 720, bookings))    # 11:00 to 12:00  -> starts as the other ends
print(has_clash(3, 630, 690, bookings))    # same time, different room

Expected output: True, False, False. The second case shows why the comparison uses < and >, not <= and >=: two bookings that only touch do not overlap. It is also a boundary test case.

Programmed Data Backup

🎯 (SE-12-04, SE-12-09)

📌 Demonstrate the use of programmed data backup

A programmed data backup copies your data automatically on a schedule or before a risky change, so you don't have to remember to do it.

Python — Programmed Data Backup Script
import shutil
from datetime import datetime

def programmed_backup(db_filepath, backup_directory):
    """Automates the backup of the project database with a timestamp."""
    timestamp = datetime.now().strftime("%Y%m%d_%H%M%S")
    backup_file = f"{backup_directory}/db_backup_{timestamp}.sqlite3"
    
    try:
        shutil.copy2(db_filepath, backup_file)
        print(f"✅ Backup successful: {backup_file}")
    except IOError as e:
        print(f"❌ Backup failed: {e}")

# Execute backup before deploying a new feature
programmed_backup('app_data.sqlite3', './backups')
Tip Test your backups by restoring one. A backup you can't restore is not a backup.

Planning what to back up

Decide the answers to five questions before writing any code. Together they make a backup strategy.

QuestionLibrary Loans answer
What is worth keeping?The loans database (cannot be recreated), the code (in Git), the documents (in cloud storage the school approves)
How often?The database every weekday at 4 pm and before any install or update. The most that could be lost is one day's loans, which the paper cards also record for the first two weeks.
Where are copies kept?A second folder on the computer and a copy on a USB drive kept in the office. A copy on the same disk does not survive a disk failure. A common rule of thumb is 3 copies, on 2 kinds of storage, with 1 kept off-site.
How many versions are kept?The latest 5, and older ones are deleted automatically so the disk does not fill.
How is it tested?Once a term, restore a backup on another computer and check that the data is there.

A more robust backup program

Copying a database file with shutil.copy2 can produce a damaged copy if the application is writing at that moment. SQLite has a built-in backup method that is safe on a live database. This version also checks the copy and prunes old backups.

Python: safe, verified backup with retention
import sqlite3
from datetime import datetime
from pathlib import Path

KEEP = 5   # how many backups to retain


def backup_database(db_path, backup_dir):
    """Copy a live SQLite database safely, check the copy, and prune old copies."""
    backup_dir = Path(backup_dir)
    backup_dir.mkdir(exist_ok=True)
    stamp = datetime.now().strftime("%Y%m%d_%H%M%S")
    target = backup_dir / f"library_{stamp}.sqlite3"

    source = sqlite3.connect(db_path)
    copy = sqlite3.connect(target)
    try:
        source.backup(copy)                      # safe even while the app is running
        ok = copy.execute("PRAGMA integrity_check").fetchone()[0] == "ok"
    finally:
        copy.close()
        source.close()

    if not ok:
        target.unlink()
        raise RuntimeError("Backup failed its integrity check and was deleted")

    old = sorted(backup_dir.glob("library_*.sqlite3"))[:-KEEP]
    for path in old:
        path.unlink()
    return target


if __name__ == "__main__":
    print("Backup written to", backup_database("library.db", "backups"))

Expected output (the file name holds the date and time of the run): Backup written to backups/library_20260930_160000.sqlite3. After more than five runs the backups folder still holds only five files.

Implementing Version Control

🎯 (SE-12-06, SE-12-09)

📌 Implement version control when developing a software engineering solution

Version control is a fundamental professional practice. Git allows engineers to track every change made to the codebase, revert to earlier versions if bugs are introduced, and collaborate without overwriting each other's work. The workflow below demonstrates the standard Git feature-branch workflow used in professional software engineering.

Bash — Git Feature-Branch Workflow
# ── INITIAL SETUP ──────────────────────────────────────────
# Initialise a new repository and make the first commit
git init library-management-system
cd library-management-system
git add README.md
git commit -m "Initial commit: project structure"

# ── FEATURE DEVELOPMENT ────────────────────────────────────
# Always create a new branch for each feature
git checkout -b feature/book-search

# After writing code, stage and commit your changes
git add src/search.py tests/test_search.py
git commit -m "Add book search by title and ISBN with unit tests"

# ── MERGING A FEATURE ──────────────────────────────────────
# Switch back to main and merge the completed feature
git checkout main
git merge feature/book-search --no-ff -m "Merge feature/book-search into main"

# ── USEFUL COMMANDS ────────────────────────────────────────
git log --oneline --graph    # View commit history as a graph
git diff HEAD~1 HEAD         # See changes since the last commit
git status                   # Check which files are staged/unstaged
git stash                    # Temporarily save uncommitted changes

# ── TAGGING A RELEASE ──────────────────────────────────────
git tag -a v1.0 -m "Version 1.0 — submitted for client review"
git push origin main --tags
Version Control Best Practices for the SEP
  • Commit frequently: Commit after every logical unit of work (e.g., after implementing one function). Small commits are far easier to review and revert than large, multi-feature commits.
  • Write meaningful commit messages: Use the imperative mood and describe what the commit does: "Add login form validation" not "fixed stuff" or "wip".
  • Use branches for features: Never code a new feature directly on main. Always create a feature branch (git checkout -b feature/my-feature) so the main branch stays stable.
  • Link to your process diary: Your commit history in GitHub serves as timestamped evidence of ongoing development — reference it in your process diary entries.

When two changes collide: a merge conflict

If the same line changes on two branches, Git cannot choose, so it stops the merge and marks the file. Suppose main lowered the limit to 4 while another branch raised it to 6:

<<<<<<< HEAD
MAX_LOANS = 4
=======

>>>>>>> feature/limit-six

Resolve it by deciding, not by picking a side automatically. The requirement (FR3) says the limit is 5, so neither is right. Edit the file to MAX_LOANS = 5, delete the three marker lines, then run git add rules.py and git commit. The Programming for the Web page covers this in more depth.

What not to commit, and how to write commits

  • Keep secrets and data out of the repository. Passwords, API keys and the live database (library.db) do not belong in Git, and once pushed they are hard to remove. List them in a .gitignore file and keep keys in environment variables. A repository on GitHub can be public.
  • One logical change per commit, with a message that says what and why: Fix off-by-one in can_borrow (BUG-002). Referring to the defect ID links the history to the defect log.
  • Review before merging. A pull request lets a peer read the change, comment and approve it before it reaches main.
  • Tag releases (git tag -a v1.0) so the exact version the client tested can always be recovered.

Know the difference between a commit (a saved version), a branch (a line of work), a merge (joining branches) and a repository (the project with its history). Common mistakes are treating version control as a backup only, and mixing up Git (the tool) with GitHub (a hosting service).

Responding to Difficulties

🎯 (SE-12-02, SE-12-04, SE-12-06, SE-12-09)

📌 Explore strategies to respond to difficulties when developing a software engineering solution

  • looking for a solution online
  • collaboration with peers
  • outsourcing

Every project hits problems. What matters is how you respond:

  • Looking for a solution online: start with official documentation, then trusted forums such as Stack Overflow. Test anything you find, and cite code you reuse.
  • Collaboration with peers: explain the problem to a classmate or ask for a code review. Often, explaining the problem is enough to spot the bug.
  • Outsourcing: use an existing service or library for a hard, non-core part, such as a payment provider or a login service.

Looking for a solution online

  1. Read the error message and copy the last line exactly (for example KeyError: 'due'). Search for it with the name of the language or library.
  2. Try official documentation first (docs.python.org, the library's own site), then established communities such as Stack Overflow.
  3. Judge the source: is it recent, does it match your version, does an accepted answer explain why it works? An answer you do not understand is a risk.
  4. Test it in isolation in a small file before it enters your project.
  5. Acknowledge it: a comment with the URL and licence, and a process diary entry. Never paste passwords, real student data or the whole project into a public forum.

Collaboration with peers

  • Explain the problem aloud to a classmate (often called rubber-duck debugging). Putting it into words often exposes the fault.
  • Ask a good question: what you expected, what happened instead, what you already tried, and the smallest code that shows the problem.
  • Pair on the difficulty: one person types while the other reads the logic, then swap.
  • Ask for a code review when a fresh pair of eyes is needed; in the earlier example, a peer spotted the time zone error.
  • Keep the work your own. A peer may explain and suggest, but you must write and understand your solution, and record the help in the process diary.

Outsourcing

Outsourcing means handing a part of the work to an outside provider: a library, a hosted service or API, or another person or company. The developer keeps the part that is specific to the client. It is sensible for a hard, well-solved, non-core part such as secure login, payments or maps. The trade-offs to weigh are cost, control, security and privacy (where the data goes), reliability of the supplier, licence terms, and the effort to connect it.

Boundary testing: choosing the data

Boundary testing tests the values on and either side of each limit, because mistakes in a comparison (< where <= was meant) show up only there. For a range, test the value just below the minimum, the minimum, just above it, a typical value, just below the maximum, the maximum and just above it. Add data of the wrong type and empty input.

Worked example (FR3): a member may hold at most 5 loans, so the valid values for the number of active loans before issuing are 0 to 4, and the member at 5 is refused. Test the edges of that rule.

Path testing: covering every route through the code

Path testing chooses test data so that every path through the code runs at least once, which means every branch of every IF. Count the paths from the algorithm: each decision splits the route.

Two decisions in a nested structure give three paths, not four, because the second decision is reached only when the first is false. Path testing and boundary testing are complementary: three well-chosen inputs cover all the paths, but only the boundary values 50 and 51 would catch a mistake such as >= 50. Both inputs return 1000, so only the path and the neighbouring inputs reveal the fault.

Unit tests in Python: expected against actual

Python's built-in unittest module runs test cases and compares each actual output with the expected one. The test methods below cover the boundaries and paths worked out above.

Python: unit tests for the loan and fine rules
import unittest


def can_borrow(active_loans, limit=5):
    """A member may borrow only while they have fewer than the limit."""
    return active_loans < limit


def calculate_fine_cents(days_overdue):
    """Return the fine in cents: 20 cents a day, capped at 1000 (ten dollars)."""
    if days_overdue <= 0:
        fine = 0
    else:
        if days_overdue > 50:
            fine = 1000
        else:
            fine = days_overdue * 20
    return fine


class TestLoanRules(unittest.TestCase):
    def test_loan_limit_boundaries(self):
        self.assertTrue(can_borrow(4))      # one below the limit
        self.assertFalse(can_borrow(5))     # at the limit

    def test_fine_not_overdue(self):
        self.assertEqual(calculate_fine_cents(0), 0)
        self.assertEqual(calculate_fine_cents(-3), 0)

    def test_fine_below_cap(self):
        self.assertEqual(calculate_fine_cents(1), 20)
        self.assertEqual(calculate_fine_cents(50), 1000)

    def test_fine_capped(self):
        self.assertEqual(calculate_fine_cents(51), 1000)


if __name__ == "__main__":
    unittest.main(verbosity=2)

Language-Dependent Code Optimisation

🎯 (SE-12-08, SE-12-09)

📌 Use a language-dependent code optimisation technique

A language-dependent optimisation uses a feature of your particular programming language to make code faster or clearer. In Python, list comprehensions and built-in functions such as sum() and sorted() run in optimised C code, so they are usually quicker than writing the same loop yourself. Measure before and after, for example with timeit, to show the change helped.

Python — Code Optimisation & Boundary Testing
import unittest

# OPTIMISED CODE: Using list comprehension instead of a slow for-loop
def get_valid_ages(age_list):
    """Returns ages between 18 and 65 (inclusive) using fast list comprehension."""
    return [age for age in age_list if 18 <= age <= 65]

# TESTING: Applying boundary testing methodology
class TestAgeValidation(unittest.TestCase):
    def test_boundaries(self):
        # Boundary data: 17 (invalid), 18 (valid), 65 (valid), 66 (invalid)
        test_data = [17, 18, 40, 65, 66]
        expected_output = [18, 40, 65]
        actual_output = get_valid_ages(test_data)

        # Comparing actual output with expected output
        self.assertEqual(actual_output, expected_output)

if __name__ == '__main__':
    unittest.main()

Language-dependent and language-independent optimisation

A language-independent optimisation improves the algorithm or the data structure and works in any language: for example, searching a sorted list with binary search instead of scanning it. A language-dependent optimisation uses a feature of your language's design or standard library. In Python that means built-in functions written in optimised C, comprehensions, and the standard data types.

Slower or clumsierPython techniqueWhy it helps
total = 0 then a for loop that adds each valuesum(values)The loop runs inside the interpreter's compiled code, not in Python bytecode

Scanning a list for a match (if x in big_list)Store items in a set or dictHash lookup takes about the same time however large the collection is
Building text with += in a loop", ".join(parts)Builds the string once instead of copying it repeatedly
Building a huge list only to loop through it onceA generator expression: sum(x * x for x in data)Produces items one at a time without holding them all in memory

Worked example: measure before and after

The Library Loans catalogue searches by ISBN. Scanning a list of 10,000 books takes longer as the catalogue grows; a dictionary keyed by ISBN is a Python data type built for lookup. Use timeit to measure the difference instead of guessing.

Python: timing a scan against a dictionary lookup
import timeit

books = [{"isbn": str(9780000000000 + i), "title": f"Book {i}"} for i in range(10_000)]
target = books[-1]["isbn"]                       # worst case for a scan
by_isbn = {b["isbn"]: b for b in books}          # built once, when the catalogue loads


def scan():
    return next((b for b in books if b["isbn"] == target), None)


def lookup():
    return by_isbn.get(target)


assert scan() == lookup()                        # same answer: the optimisation is safe
print("scan  :", round(timeit.timeit(scan, number=200), 4), "seconds for 200 searches")
print("lookup:", round(timeit.timeit(lookup, number=200), 6), "seconds for 200 searches")

def total_loop(values):
    total = 0
    for v in values:
        total += v
    return total

data = list(range(100_000))
print("loop  :", round(timeit.timeit(lambda: total_loop(data), number=100), 3))
print("sum() :", round(timeit.timeit(lambda: sum(data), number=100), 3))

Expected output: four lines of timings. The exact numbers depend on the computer, so record your own. In a test run the dictionary lookup was thousands of times faster than the scan, and sum() was several times faster than the hand-written loop. The assert line matters as much as the timings: an optimisation that changes the answer is a defect.

Rules for optimising

  1. Make it correct first. Optimise only code that passes its tests.
  2. Measure, then change. Record the timing before and after, on the same data.
  3. Re-run the tests after every optimisation, to show behaviour is unchanged.
  4. Do not trade away readability for a trivial gain. Optimise where a requirement (such as NFR1's 2 seconds) is at risk.

📌 Analyse and respond to feedback

Feedback from your client, users and peers shows how well the solution meets its requirements. Analyse it to find patterns, then respond by deciding what to change, what to schedule for later and what to explain.

Turning feedback into action

  1. Collect: use the same short questions after each round, such as a 1–5 ease-of-use rating plus one open question.
  2. Group: sort comments into usability, bugs, performance and new features.
  3. Prioritise: fix what blocks users first; schedule features for later versions.
  4. Respond: tell users what changed, and retest to check the fix worked.

Evaluating the Effectiveness of Your Solution

🎯 (SE-12-08, SE-12-09)

📌 Evaluate the effectiveness of a software engineering solution

  • developing a report to synthesise feedback
  • developing a test plan
  • testing data used/generated based on path and boundary testing
  • comparing actual output with expected output

Effectiveness & Testing Data

Evaluation involves generating a test plan and executing it using rigorous testing data based on path testing (ensuring every path through the code, and so every branch, executes at least once) and boundary testing (testing the extreme limits of input constraints). Engineers evaluate success by comparing actual output with expected output, and develop a final report to synthesise client feedback.

Test Plan Template

A test plan is a document that outlines the testing strategy, scope, resources, schedule, and exit criteria for a software project. It is prepared before testing begins to ensure testing is systematic and complete.

Evaluating Against Requirements

A thorough evaluation compares what you built against what you planned from Phase 1. For each functional and non-functional requirement, document:

  • Was this requirement fully met? Partially? Not met?
  • What evidence demonstrates it is met? (test results, user feedback, system output)
  • If not fully met, what limited the implementation?

Developing an Evaluation Report

Your evaluation report should synthesise all feedback gathered throughout the project and systematically compare actual outputs with expected outcomes. This includes:

  • Requirement Coverage: Use your original requirements document and reference each requirement by number, demonstrating which were fully met, partially met, or deferred.
  • Testing Evidence: Present test results showing how the system behaves against your test data (path and boundary testing cases).
  • User Feedback: Document feedback from the client or stakeholders about whether the system meets their needs.
  • Technical Evaluation: Discuss decisions made, challenges encountered, and how they were addressed.

To synthesise feedback is to combine several sources into a few conclusions, not to list each comment. A worked excerpt for Library Loans:

Feedback came from Mrs Chen (two reviews and the acceptance test), two volunteers (observed tasks) and eight testers (a rating survey). Three themes appeared across sources. (1) Findability: five of eight testers could not find the loan history; after the menu change the mean ease-of-use rating rose from 3.1 to 4.4. (2) Speed: Mrs Chen and two testers said search felt slow, and a timed test confirmed 4 seconds against the 2-second target (NFR1); an index reduced this to 0.3 seconds. (3) Missing reminders: raised by Mrs Chen and three testers. This is outside the version 1 boundary, so it is recommended for version 2, after a privacy review. Because the sample was small, these results show a likely improvement, not a certain one.

Evaluation Best Practices
Be specific and evidence-based — reference your test results and requirements document by number.
Acknowledge any limitations honestly — explain what didn't work and why, demonstrating critical reflection.
Use actual data — show test output, user feedback quotes, and measurable results rather than general statements.
